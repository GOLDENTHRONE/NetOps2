# p22.txt — P0 Live Verification Plan (for Copilot)

------------------------------------------------------------------------------
0. READ THIS FIRST — what P0 is, and what it is NOT (critical)
------------------------------------------------------------------------------
P0's code path is the SAME on every route (the `AuthRoute` one-shot auth check
+ `ClusterAccessGate` screen, and the All Clusters status poll). So "test every
page" does NOT mean different code per page — it means navigate through every
section and confirm the ONE code path behaves consistently everywhere.

P0 IS (verify all of this now):
  1. All Clusters tab status is truthful — a single blip must NOT show a false
     "Unavailable"; a real 401/403 must show immediately; recovery is quick.
  2. The ONE-SHOT auth check when opening a cluster + its screens
     (Checking / Not responding / Session expired / Access limited).

P0 is NOT (if you see this, log it as "P1 known-gap", NEVER "P0 fail"):
  - Sitting INSIDE a cluster and, WITHOUT navigating, expecting the gate to
    appear/disappear on its own. The inside auth check is one-shot (no poll,
    no focus refetch), so it only re-checks on navigation/remount. Auto-recovery
    of that is P1, not P0. The gate SHOULD appear when you navigate to a new
    page (that re-fires the one-shot) — that part IS P0.
  - Live list/data loading speed inside a cluster (pods/logs streaming) — that
    is P1 (watch/WebSocket). Do not fail P0 if data is slow to appear.

Expected values below come from the ACTUAL code:
  - Healthy status poll: every ~10s, with +/-15% jitter => 8.5s – 11.5s
  - Backoff on consecutive failures: 10s, 10s, 20s, 30s, 30s ... (cap 30s), +/-15%
  - Tab-focus recheck: instant (refetchOnWindowFocus: 'always' on the polls)
  - Cluster-open blip: exactly 1 retry after ~1s (+/-15% => 0.85s–1.15s)
  - Per-attempt auth timeout: 15s (AUTH_TIMEOUT_MS)
  - keep-last-good: needs 2 consecutive failures before the row goes "Unavailable"
    (STATUS_FAIL_THRESHOLD = 2)
  - 401/403: immediate, NO retry, NO backoff (poll stays at base 10s)

------------------------------------------------------------------------------

2. Open Chrome DevTools (F12).

NOTE on "capture every event with time": the most accurate no-code-change way
is the Network tab timings + HAR export. If more granular in-code timestamped

NOTE on masking: use generic placeholders in the report — <your-cluster>,
<username>, <password>. Never paste real cluster URLs, usernames, tokens or
passwords into the results file.

  2. Network filter: `version` (and/or `selfsubjectrulesreviews`).

------------------------------------------------------------------------------
SCENARIO 2 — One blip must NOT show false "Unavailable" (keep-last-good)
------------------------------------------------------------------------------
Check: a single failed poll keeps the row reachable; needs 2 to flip.
Steps:
  1. On All Clusters, pick a reachable cluster (Reachable/Ready).
  2. Network → right-click its `version` request → "Block request URL"
     (or throttle so one request times out) for ONE cycle only.
  3. Confirm the row STAYS Reachable (keep-last-good), maybe a subtle
     "reconnecting" hint. It must NOT show "Unavailable".
  4. Unblock → next poll → row normal.
  5. Now keep it blocked for 2+ cycles → "Unavailable" SHOULD appear (honest).
Capture: screenshots + timestamps for both cases.
PASS: 1 fail = still Reachable; 2 fails = Unavailable.
FAIL: Unavailable on the very first fail.

------------------------------------------------------------------------------
SCENARIO 3 — Backoff curve when a cluster stays down (10 -> 10 -> 20 -> 30)
------------------------------------------------------------------------------
Check: consecutive-failure poll gaps grow ~10s, ~10s, ~20s, ~30s, ~30s (+/-15%).
Steps:
  1. Make one cluster continuously unreachable (block its version/auth URL).
  2. Note the gaps between `version` requests from the start.
  3. Expected (+/-15%): 1st->2nd ~10s, 2nd->3rd ~10s, 3rd->4th ~20s,
     4th->5th ~30s, then ~30s cap.
  4. Unblock → on the next poll (within ~30s) the row returns to Reachable.
Capture: HAR + gap-sequence table.
PASS: gaps 10->10->20->30 cap; recovery <= ~30s.
FAIL: gaps reach 60s+ or it never recovers.
