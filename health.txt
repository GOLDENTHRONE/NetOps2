1. WHAT "APPLICATION" MEANS HERE (no separate Application object exists)
--------------------------------------------------------------------------------
- Headlamp has NO "Application" API resource. An "Application" in the
  Applications tab = one auto-discovered Kubernetes NAMESPACE.
- Discovery code:
  File: frontend/src/components/project/ProjectList.tsx
  Function: discoverProjectsFromNamespaces(namespaces)
    - Takes every Namespace object returned from ALL configured clusters.
    - Groups by metadata.name (so a namespace named "wnv7a0vbgw0013c" that
      exists in several clusters collapses into ONE application row whose
      `clusters` field lists every cluster it appears in).
    - Filters out system namespaces via isSystemNamespace() in
      frontend/src/components/project/projectUtils.ts:
        SYSTEM_NAMESPACE_PREFIXES = ["openshift-", "kube-", "open-cluster-management"]
        SYSTEM_NAMESPACE_NAMES    = ["default","openshift","kube-system",
                                      "kube-public","kube-node-lease"]
  So application "wnv7a0vbgw0013c" = the Kubernetes Namespace object named
  "wnv7a0vbgw0013c", surviving that filter.

2. API CALL #1 — LIST NAMESPACES (produces the list of "applications")
--------------------------------------------------------------------------------
Triggered by: useProjects() -> Namespace.useList({ clusters: [...] })
  File: frontend/src/components/project/ProjectList.tsx (useProjects)
  Underlying hook chain: lib/k8s Namespace class -> KubeObject.useList (v2 API)
                          -> frontend/src/lib/k8s/api/v2/useKubeObjectList.ts
                          -> kubeObjectListQuery()

Request (per cluster, sent through Headlamp's own backend, not directly to k8s):
  Method : GET
  URL    : /clusters/<clusterName>/api/v1/namespaces
           (built by KubeObjectEndpoint.toUrl() + makeUrl(), prefixed by
            clusterFetch() which inserts "clusters/<cluster>/" — see
            frontend/src/lib/k8s/api/v2/fetch.ts:clusterFetch)
  Full example for this app's cluster:
    GET http://<headlamp-host>:<port>/clusters/default--api-wnv7a0-wnvlil-itn-3pc-att-com:6443--at9306/api/v1/namespaces

  Headers added by frontend before send (frontend/src/lib/k8s/api/v2/fetch.ts):
    - credentials: 'include' (cookies)
    - Headers from getHeadlampAPIHeaders() (Headlamp session/auth headers)
    - Headers from addBackstageAuthHeaders() (if running embedded in Backstage)
    - If a stateless/dynamic kubeconfig is used for that cluster:
        KUBECONFIG: <base64 kubeconfig>
        X-HEADLAMP-USER-ID: <user id from localStorage>

  Response (standard Kubernetes NamespaceList, proxied verbatim from the
  cluster's kube-apiserver, only trimmed of `metadata.managedFields` client-side):
    {
      "kind": "NamespaceList",
      "apiVersion": "v1",
      "metadata": { "resourceVersion": "123456" },
      "items": [
        {
          "metadata": {
            "name": "wnv7a0vbgw0013c",
            "uid": "...",
            "resourceVersion": "...",
            "creationTimestamp": "...",
            "labels": {...},
            "annotations": {...}
          },
          "spec": { "finalizers": ["kubernetes"] },
          "status": { "phase": "Active" }
        },
        ... more namespaces ...
      ]
    }

  If the cluster restricts namespace visibility (allowedNamespaces /
  allowedNamespacesSelector, see loadClusterSettings), Headlamp instead does
  per-name GETs: GET /clusters/<cluster>/api/v1/namespaces/<name>
  (allowedNamespaceListQuery() in useKubeObjectList.ts) and merges results —
  same final shape, one namespace object per allowed name.

  Live updates: after the initial GET, Headlamp either:
    a) opens a WATCH (adds queryParams watch=1 to the same REST path) — the
       "legacy" per-request WebSocket path (frontend/src/lib/k8s/api/v2/webSocket.ts), OR
    b) if REACT_APP_ENABLE_WEBSOCKET_MULTIPLEXER=true, subscribes over a single
       shared multiplexed WebSocket:
         URL: ws(s)://<host>/wsMultiplexer  (MULTIPLEXER_ENDPOINT,
              frontend/src/lib/k8s/api/v2/multiplexer.ts)
         Sub-protocol: "headlamp.multiplexer.k8s.io" (+ backend token protocol)
         One JSON control message per (cluster, path, query) tells the backend
         which resource/cluster/namespace to start streaming; backend
         multiplexes many k8s watch streams over that one socket connection.

4. HOW THE HEALTH STATUS IS COMPUTED (frontend-only, no backend "health" API)
--------------------------------------------------------------------------------
There is NO dedicated backend "/health" endpoint for applications. Health is
derived entirely in the frontend from the raw Kubernetes objects fetched in
step 3.

  File: frontend/src/components/resourceMap/nodes/KubeObjectStatus.tsx
  Function getStatus(obj) returns one of: 'success' | 'warning' | 'error'
    - Pod            -> getPodStatus():
                          phase 'Failed'              => error
                          phase 'Succeeded'           => success
                          phase 'Running' + Ready=True => success
                          phase 'Running' + Ready!=True=> warning
                          phase 'Pending'             => warning
                          else                        => success
    - Deployment / ReplicaSet / StatefulSet / DaemonSet:
                          readyReplicas < totalReplicas => warning, else success
                          (getReadyReplicas/getTotalReplicas in lib/util)
    - everything else (ConfigMap, Secret, Service, Ingress, PVC, Job, CronJob,
      NetworkPolicy, HPA, Role, RoleBinding, ResourceQuota, LimitRange, ...):
                          always 'success' (no failure semantics modeled)

  File: frontend/src/components/project/projectUtils.ts
  Function getResourcesHealth(resources) =
      lodash countBy(resources, getStatus)
    -> returns { success: n, warning: n, error: n } tally across ALL objects
       gathered for the application (every kind, every cluster it spans).

  ProjectList.tsx 'health' column Cell logic (per application row):
      items.length === 0        -> "No Resources" / rank 0 / help-circle icon
      projectHealth.error   > 0 -> "Unhealthy"     / rank 3 / status="error"
      projectHealth.warning > 0 -> "Degraded"      / rank 2 / status="warning"
      else                       -> "Healthy"       / rank 1 / status="success"
  Icon: getHealthIcon(success, error, warning) ->
      no items          => mdi:help-circle
      error   > 0       => mdi:alert-circle
      warning > 0       => mdi:alert
      else              => mdi:check-circle
  Displayed via <StatusLabel status="error|warning|success"> (frontend/src/components/common).

  Concretely for "wnv7a0vbgw0013c" (shown "Healthy" in the screenshot):
    - Headlamp fetched the 19 default-kind lists scoped to namespace
      "wnv7a0vbgw0013c" across every cluster the namespace exists in.
    - Every Pod-bearing owner (Deployment/StatefulSet/DaemonSet/ReplicaSet)
      in that namespace has readyReplicas == totalReplicas, AND no fetched
      object evaluated to 'error' or 'warning' via getStatus().
    - error=0, warning=0, success=N (N = total object count across 19 kinds)
      -> rank 1 -> "Healthy" badge with green check-circle icon.
  "Resources" column = items.length (raw count across the same 19 kinds).

5. BACKEND ROLE (transport / auth / caching only — no health logic here)
--------------------------------------------------------------------------------
The Go backend never computes health. It is a reverse proxy + auth + cache
layer sitting between the frontend and each cluster's kube-apiserver.

  a) Reverse proxy (actual k8s API forwarding):
     File: backend/pkg/kubeconfig/kubeconfig.go
     - Context.SetupProxy() builds an httputil.ReverseProxy pointed at
       c.Cluster.Server (the cluster's kube-apiserver URL from its kubeconfig),
       with a RoundTripper built from the cluster's rest.Config (handles
       TLS/OIDC/exec-based auth transparently) and a custom User-Agent.
     - Context.ProxyRequest(w, r) calls proxy.ServeHTTP(w, r) — this is what
       actually executes every "GET /clusters/<cluster>/api/..." request
       against the real API server and streams the JSON response back
       unmodified (after stripping upstream CORS headers it doesn't own).
     - On OIDC clusters, a 401 from the API server is logged with a hint
       (token expired / issuer mismatch) but the error is still passed
       through to the frontend as-is.

  b) Routing / auth middleware:
     File: backend/pkg/auth/auth.go, middleware.go
     - clusterPathRegex = ^/clusters/([^/]+)/.* extracts the cluster name
       from the URL and resolves which kubeconfig Context.ProxyRequest to
       call for it.
     - Validates cookies/bearer tokens/proxy-auth headers before allowing the
       request through (backend/pkg/auth/cookies.go, backendtoken.go).

  c) Response cache (read-side optimization, no semantic change to data):
     File: backend/pkg/k8cache/cacheStore.go, cacheInvalidation.go
     - Caches GET responses for /api and /apis paths (incl. proxied
       /clusters/<name>/... variants) to reduce load on the upstream API
       server for repeated LIST calls (e.g. re-renders of the Applications
       table refetching the same 19 resource kinds every 60s).
     - Invalidated on writes/watch events so cached lists don't go stale
       past what a watch event indicates.
     - Never touches or interprets object status fields — purely a
       request/response byte cache keyed by path+query+cluster.

  d) WebSocket multiplexing (only used when
     REACT_APP_ENABLE_WEBSOCKET_MULTIPLEXER=true):
     - Backend-side multiplexer (WebSocketMultiplexer interface referenced
       from backend/pkg/headlampconfig/headlampConfig.go) accepts one
       WebSocket per browser tab and internally opens/watches the real
       k8s watch streams per (cluster, resource, namespace) subscription
       requested by the frontend's WebSocketManager, forwarding raw watch
       events (ADDED/MODIFIED/DELETED) back down the single socket tagged
       with the subscription's key. The frontend applies these events to
       its react-query cache (KubeList/useWatchKubeObjectLists), which is
       what causes the Health/Resources cells to re-render live.

--------------------------------------------------------------------------------
  Browser (ProjectList.tsx)
    -> GET /clusters/<cluster>/api/v1/namespaces                (discover apps)
    -> filter system namespaces -> row "wnv7a0vbgw0013c" appears
    -> mount Resources+Health cells for that row
    -> GET x19 /clusters/<cluster>/{api|apis/...}/namespaces/wnv7a0vbgw0013c/<kind>
       (parallel, one per default resource kind, refetch every 60s since
        disableWatch=true in the table)
  Go backend (kubeconfig.go, auth.go, k8cache)
    -> authenticates the request, resolves cluster context by name,
       (maybe serves from cache), reverse-proxies to kube-apiserver,
       returns raw Kubernetes JSON unchanged.
  Browser (again)
    -> KubeObject.useList wraps each item's JSON into typed KubeObject
       instances (strips managedFields, sets .cluster)
    -> useProjectItems/useKubeLists flattens all 19 lists into one `items[]`
    -> getResourcesHealth(items) tallies success/warning/error via getStatus()
    -> health column renders "Healthy"/"Degraded"/"Unhealthy"/"No Resources"
       purely from that client-side tally — no server-computed health value
       is ever sent over the wire.
