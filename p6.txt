4. DIAGNOSIS IS NOT HEALTH
============================================================

Diagnosis is an ADDITIVE, READ-ONLY evidence layer.

A diagnosis:

- MUST NOT vote on application health.
- MUST NOT change application state.
- MUST NOT change workload state.
- MUST NOT affect worst-of-roots.
- MUST NOT affect health counts.
- MUST NOT affect deduplication.
- MUST NOT create another health-bearing resource.
- MUST NOT change which resource is considered the aggregation root.

Think of the architecture as:

Existing health calculation
        |
        v
Existing aggregation/deduplication
        |
        v
Existing application health result
        |
        +----> NEW diagnosis/evidence collection
                    |
                    v
                 UI only

Diagnosis must NEVER feed back into health calculation.

============================================================
8. DIAGNOSIS MUST BE CONSERVATIVE
============================================================

Never guess.

Never infer causality when the repository only provides
correlation evidence.

Use wording such as:

"ConfigMap X is referenced by Pod Y but was not found."

NOT:

"ConfigMap X caused the application failure."

Diagnosis must only be produced when the required evidence is
actually available.

If evidence is incomplete:

NO DIAGNOSIS.

Prefer a missing diagnosis over a false-positive diagnosis.

============================================================
9. POD-SIGNAL GATING
============================================================

For dependency-related diagnoses, use conservative AND-gating.

A dependency diagnosis requires ALL required conditions:

A. The dependency is actually referenced by the workload/Pod.

B. The dependency is missing/unusable/problematic.

C. There is a concrete relevant Pod failure signal.

Allowed Pod signals must come from already-fetched Pod status.

Examples of valid signals include:

- Pod phase = Pending
- CreateContainerConfigError
- CreateContainerError
- ImagePullBackOff
- ErrImagePull
- CrashLoopBackOff
- ContainerCannotRun
- an explicitly supported PVC mount-wait/Pending signal

Do NOT use:

- Events
- Logs
- speculative assumptions
- generic Pod existence
- generic workload degradation
- timestamps alone
- resource age alone

If the dependency is missing but the Pod is healthy/running/ready:

NO DIAGNOSIS.

That situation is informational only.

============================================================
10. CONFIGMAP / SECRET DIAGNOSIS
============================================================

A ConfigMap or Secret diagnosis should require:

1. The workload/Pod actually references it.
2. The referenced object is absent from the fetched data.
3. The correlated Pod has a concrete failure signal.

If all three are true:

Create a diagnosis.

Example wording:

"ConfigMap 'app-config' is referenced by Pod 'web-abc',
but the ConfigMap was not found; the Pod reports
CreateContainerConfigError."

The wording must clearly communicate:

- what was referenced
- what was missing
- which Pod is affected
- what concrete Pod signal exists

Do not claim causation.

If the ConfigMap/Secret is unreferenced:
NO DIAGNOSIS.

If it is referenced but the workload is healthy:
NO DIAGNOSIS.

============================================================
11. PVC DIAGNOSIS
============================================================

PVC must not independently degrade application health.

A PVC can participate in diagnosis only when there is sufficient
correlation evidence.

For example:

- PVC is referenced by a workload/Pod.
- PVC is Pending or Lost.
- The correlated Pod is actually affected/failing or waiting
  in a relevant way.

Then a diagnosis may be produced.

If the PVC is Pending/Lost but no affected workload/Pod exists:

INFORMATIONAL ONLY.

Do not create a health vote.

Do not create a second health degradation.

============================================================
12. SERVICE DIAGNOSIS
============================================================

Use Service selector semantics.

Match:

Service.spec.selector
against
Pod.metadata.labels

using normal label-map subset/equality semantics.

Only consider in-scope fetched Pods.

A Service diagnosis requires:

1. The Service selector matches at least one relevant application
   Pod.
2. The matching Service has zero ready backends.

EndpointSlice is the preferred readiness source when already
fetched.

Endpoints is the fallback only when EndpointSlice data for that
Service is not available.

Do not perform a new API fetch.

If there is no matching application Pod:

NO DIAGNOSIS.

Do not diagnose an unrelated Service merely because it has the
same name or namespace.

Do not use name/namespace matching as a substitute for selector
matching.

============================================================
13. SERVICE READINESS
============================================================

Readiness priority:

1. EndpointSlice
2. Endpoints fallback

Zero ready addresses across the relevant matching slices/subsets
can support the Service diagnosis.

If readiness data is unavailable because the required resource
was not fetched:

Do not invent a result.

Treat it as informational/no diagnosis according to the existing
rules.

============================================================
14. QUOTA / LIMITRANGE
============================================================

Do not diagnose quota or LimitRange problems merely because a
quota/LimitRange object exists.

A quota-related diagnosis requires concrete evidence from an
already-fetched affected Pod.

For example:

- Pod is Pending.
- Pod status contains an explicit quota-related reason/string.
- The Pod is in scope.

Then a quota diagnosis may be produced.

If a quota exists but no affected Pod signal exists:

INFORMATIONAL ONLY.

Do not fetch Events to discover quota rejection.

Do not guess that quota caused the Pending state.
