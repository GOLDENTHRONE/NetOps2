==================================================
1. REQUIRED HEALTH-BEARING STATUS DATA
==================================================

Health-bearing workload resources must distinguish:

- valid observed zero
- missing/absent status data

Never convert missing status fields into fabricated zero values.

For Deployment:
- if required status fields needed for health evaluation are absent -> Unknown
- an actual observed value of 0 remains a valid value

For StatefulSet:
- same rule for required ready/replica status

For DaemonSet:
- same rule for required desired/ready status

Do not use `?? 0` or equivalent fallback where it turns missing required health evidence into a real zero.

Add unit tests for:
- complete status
- actual zero
- missing status
- partially missing status

Expected behavior:
absence of required health evidence must not become evidence of health or degradation.

==================================================
2. SUPPORTING/NON-VOTING RESOURCE LOADING
==================================================

Supporting/non-health-bearing resources must NOT independently block the primary health verdict.

Examples include:
- Service
- EndpointSlice
- HPA
- CronJob
- ConfigMap
- Secret
- NetworkPolicy
- other supporting resources already excluded from primary health evaluation

If Pods/Deployments/etc. have complete health evidence and a supporting resource is still loading or returns a non-voting API error:

Primary health must remain based on the health-bearing resources.

Do NOT allow global `isLoading` to turn the whole application into blocking Unknown.

Preserve supporting-resource failures/loading as non-blocking observability information where appropriate.

Add tests for:
- healthy workload + Service loading
- healthy workload + HPA loading
- healthy workload + multiple supporting kinds loading
- healthy workload + supporting kind returns 403
- all health-bearing resources complete while supporting resources remain loading

Expected:
primary health remains Healthy.

==================================================
3. JOB STATE PRECEDENCE
==================================================

Fix Job evaluation precedence.

Required order:

1. complete=True -> Healthy
2. terminal failed=True / terminal failure -> Unhealthy
3. active > 0 -> Progressing
4. succeeded > 0 AND active == 0 -> Healthy
5. otherwise Unknown/empty according to existing model

CRITICAL CASE:

spec.completions = 3
status.succeeded = 1
status.active = 2

Expected:
Progressing

NOT Healthy.

Also test:

A. completions=3, succeeded=3, active=0 -> Healthy
B. succeeded=1, active=2 -> Progressing
C. failed=True / terminal failure -> Unhealthy
D. retry history failed previously, then complete=True -> Healthy
E. succeeded>0, active=0 without complete flag -> Healthy only if existing semantics explicitly support this
F. missing required Job status -> Unknown where evidence is insufficient

Do not allow `succeeded > 0` to override currently active work.

4. NAMESPACE DISCOVERY FAILURE
==================================================

Review how Application rows are created.

A cluster/namespace discovery failure must not silently make cluster-only applications disappear from the UI.

Preserve enough cluster/namespace provenance to represent:

- successful namespace discovery
- failed namespace discovery
- cluster reachable but namespace inventory unavailable

Add unit tests for:
- successful namespace discovery
- namespace discovery failure on one cluster while another cluster succeeds
- cluster-only application when namespace inventory is unavailable

Do not redesign ApplicationHealth.
