KUBERNETES HEALTH MODEL
========================

The fundamental rule should be:

A resource should contribute to APPLICATION HEALTH only when its own Kubernetes status is authoritative evidence of that resource's runtime/execution state.

Separate resources into three conceptual layers:

1. EXECUTION / HEALTH LAYER
   -------------------------
   These resources can vote on Application Health because their own status represents runtime/execution state.

   Examples:
   - Deployment
   - StatefulSet
   - DaemonSet
   - ReplicaSet, only when it is a root/standalone workload and is not already represented by an owning Deployment
   - Pod, only when it is a root/standalone workload and is not already represented by a fetched controller
   - Job, only when it is a root/standalone execution and is not already represented by a CronJob
   - CronJob, according to the existing getHealth() semantics

   Preserve existing ownerReference-based deduplication.

2. CONDITIONAL DEPENDENCY / DIAGNOSIS LAYER
   -----------------------------------------
   These resources should NOT independently make an otherwise healthy Application unhealthy.

   They can become diagnostic evidence when there is a concrete relationship to an unhealthy/failing workload.

   Examples:
   - PVC
   - ConfigMap
   - Secret
   - ResourceQuota / LimitRange

3. EVIDENCE / INFORMATIONAL LAYER
   --------------------------------
   These resources should not vote on workload health.

   Examples:
   - Service
   - Endpoints
   - EndpointSlice
   - Ingress / Gateway / Route where supported by the existing repository
   - HPA
   - NetworkPolicy
   - RBAC
   - unreferenced ConfigMap/Secret/PVC
   - other supporting resources

The key principle is:

DO NOT infer workload health merely because a supporting Kubernetes object exists or has a non-ideal condition.

HEALTH AGGREGATION
==================

Preserve the existing ownerReference-based deduplication.

The existing getAggregationRootIds() logic is important and must not be replaced.

A controller hierarchy such as:

Deployment -> ReplicaSet -> Pod

or

CronJob -> Job -> Pod

must not produce multiple independent health votes for the same workload.

Health aggregation must continue to operate on the deduplicated health-bearing ROOT resources.

For multiple independent root workloads within the current Application scope:

- aggregate using the existing worst-of-roots behavior
- do not let supporting/diagnostic resources introduce additional health votes
- do not double count Pods, ReplicaSets, Jobs, etc.

DIAGNOSIS MODEL
===============

Introduce a separate diagnosis concept.

Diagnosis must NEVER directly change the calculated health state.

Instead:

health = authoritative workload state

diagnoses = evidence explaining potentially relevant problems

A diagnosis should only be emitted when there is a concrete, defensible correlation between a resource and an Application workload.

Do NOT produce speculative diagnoses.

SERVICE DIAGNOSIS
=================

For a Service:

- Do NOT make Service health a health vote.
- Do NOT diagnose a Service merely because it has zero endpoints.
- First establish that the Service selector actually matches Pods belonging to the Application's fetched workload.
- Use Kubernetes selector semantics / label matching, not name-prefix guessing.
- Only inspect Pods already present in the fetched resource set.
- If the Service selector matches an in-scope Pod set AND the Service's Endpoints/EndpointSlice has zero ready addresses, emit a diagnosis such as:

  "Service <name> has no ready backends"

- The Application workload's health must remain unchanged because of this diagnosis.

If the Service selector does not match any in-scope Pods, treat it as unrelated/informational and do not create a diagnosis.

Do not modify relations.tsx or other shared relationship code to accomplish this.

If necessary, create a small local read-only selector matching helper inside the health feature.

CONFIGMAP / SECRET DIAGNOSIS
============================

Do not make every ConfigMap/Secret a health vote.

Inspect already-fetched workload/Pod templates for references through mechanisms such as:

- env.valueFrom.configMapKeyRef
- env.valueFrom.secretKeyRef
- envFrom.configMapRef
- envFrom.secretRef
- volumes.configMap
- volumes.secret

Only create a dependency diagnosis when:

1. A fetched/in-scope workload actually references the ConfigMap/Secret.
2. The referenced object is missing from the fetched resource set / known resources.
3. There is evidence that the workload is actually affected/failing, where such evidence is available from the existing fetched data.

For example:

missing Secret + CreateContainerConfigError / equivalent relevant Pod failure
    => diagnosis

missing ConfigMap + healthy/running workload
    => do NOT degrade Application health
    => preferably informational or no diagnosis

Unreferenced missing/unused ConfigMap/Secret
    => informational / no diagnosis

Do not invent Kubernetes failure reasons that cannot be derived from the current fetched data.

PVC DIAGNOSIS
=============

Be particularly careful here.

Before changing PVC behavior, inspect the existing PVC implementation and tests.

A PVC being Pending/Lost does NOT automatically mean the Application is unhealthy.

A PVC should only be treated as a conditional dependency when a fetched/in-scope workload actually references/mounts it.

Therefore:

- unused Pending PVC => informational, no Application health degradation
- referenced PVC + workload is affected/failing in a way supported by existing data => diagnosis
- referenced PVC that is healthy/usable => no diagnosis
- do not independently vote unhealthy merely because PVC.phase is Pending/Lost

If the existing implementation currently treats PVC as a direct health vote, isolate/remove that direct vote only within the Application Health feature, while preserving unrelated/shared PVC behavior elsewhere.

RESOURCE QUOTA / LIMITRANGE
===========================

Do not make ResourceQuota/LimitRange a direct health vote.

Only produce diagnosis when existing fetched Pod status gives a concrete quota-related Pending reason.

For example:

Pod Pending + explicit quota-related reason
    => diagnostic evidence

Quota exists but no affected workload is observed
    => informational

Do NOT add event API fetching.
