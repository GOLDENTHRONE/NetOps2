1. AGENDA — what we are doing
--------------------------------------------------------------------------------
Change the Applications tab so that EVERY ROW IS EXACTLY ONE APPLICATION
INSTANCE IN ONE CLUSTER AND ONE NAMESPACE, each with its own independently
computed health status.

Hard constraint: nothing else may change. No other tab (especially "All
Clusters"), no shared hook, no other functionality.

--------------------------------------------------------------------------------
2. HOW THE APPLICATIONS TAB WORKS TODAY (established by reading the code)
--------------------------------------------------------------------------------
- Sidebar "Applications" -> route "/projects" -> components/project/ProjectList.tsx.
  Details route "/project/:name" -> components/project/ProjectDetails.tsx.
  Internally the code calls these "projects"; the UI calls them Applications.
- There is no separate "application" object. An application IS a namespace:
  discoverProjectsFromNamespaces() lists every namespace the token can see and
  drops system/infrastructure ones (isSystemNamespace in projectUtils.ts).
  Application name = namespace name.
- Health is computed CLIENT-SIDE, in two layers (localHealth.ts):
  (a) per resource — localGetItemStatus() returns
      success | warning | error | progressing | unknown
      (Pod CrashLoopBackOff/ImagePullBackOff -> error; Running-but-not-Ready ->
       warning; Pending/rollout -> progressing; Deployment/StatefulSet/DaemonSet
       compare desired vs ready/updated; Endpoints with no ready pods behind a
       Service -> warning; PVC Lost -> error; etc.)
  (b) per application — getLocalHealth() takes the WORST severity:
      any error -> Unhealthy | any warning -> Degraded | any progressing ->
      Progressing | any unknown -> Unknown | else Healthy.
      No resources -> "No Resources"; resources but no workload -> "No Workloads";
      fetch failed -> "Unavailable".
  It is binary worst-case, not proportional: 1 bad pod out of 100 = Unhealthy.
- Job, CronJob and HorizontalPodAutoscaler are NON_HEALTH_BEARING: their
  problems appear under "Needs Attention" but never change the badge. Job-owned
  Pods (Helm hooks) and Deployment-owned ReplicaSets are likewise excluded.
- Refresh: 60-second POLLING, not a live watch (REFETCH_INTERVAL_MS = 60_000 in
  useProjectResources.ts and useLocalHealthItems.ts; watch is disabled).
  Health is computed lazily per VISIBLE row, so sorting only reflects rendered rows.
- Caveat worth knowing: useKubeLists caps at MAX_ITEMS = 1000 per kind and DROPS
  a kind entirely if it exceeds that, silently. Large namespaces can therefore be
  judged on incomplete data. Pre-existing; not addressed here.

--------------------------------------------------------------------------------
3. THE PROBLEM — three real defects
--------------------------------------------------------------------------------
Today discoverProjectsFromNamespaces() GROUPS BY NAMESPACE NAME, so a namespace
existing in several clusters collapses into ONE row spanning all of them, and
health is computed over the POOLED resources of every cluster. Therefore:
 (a) MASKING — healthy in cluster-A, one crashing pod in cluster-B reads as a
     single "Unhealthy" row with no way to see which cluster is at fault.
 (b) FALSE "UNAVAILABLE" — LocalHealthCell uses only the FIRST fetch error, so one
     unreachable cluster marks the whole application Unavailable even when the
     others are perfectly healthy.
 (c) NO ATTRIBUTION — LocalHealthEvidence has kind/namespace/name but NO cluster,
     so even the popover cannot say which cluster a failing resource is in.

--------------------------------------------------------------------------------
4. THE DECISION (and the alternative we rejected)
--------------------------------------------------------------------------------
Chosen: FLAT model — one row per (cluster, namespace).
A deployed instance genuinely lives in exactly one cluster + one namespace, so
this is the most truthful representation, and the health algorithm needs NO
change: each row fetches a single cluster + namespace, so getLocalHealth()
already describes exactly one instance.

Considered and rejected for now: a GROUPED/expandable model (parent row per
logical app with per-cluster child rows). It preserves a fleet-wide "is this app
OK everywhere?" line, but it is more work and was explicitly not wanted.
Honest trade-off accepted: with the flat model there is NO fleet rollup row, and
the list is longer on multi-cluster fleets. A grouped parent row can be added
later on top of these instance rows — additive, not a rewrite.

Note: auto-discovery never put multiple namespaces in one application; the only
collapsing was same-named namespaces across clusters. That is what this removes.

5. WHAT WE ACHIEVED SO FAR (the honest journey, including mistakes)
--------------------------------------------------------------------------------
5.1 Isolation was proven. Only ONE file outside components/project/ needs to
    change: the single projectDetails entry in lib/router/index.tsx.
    Correction to an earlier wrong claim: App/Home/index.tsx (the "/" page) DOES
    import ProjectList — All Clusters and Applications are the SAME Home
    component switched by a `view` state ('clusters' | 'projects'). That is a
    shared container, but the cluster list renders a different component
    (ClusterTable), so changing ProjectList's internals does not change the
    All Clusters view. Shared hooks (useKubeLists in advancedSearch/utils, and
    Namespace.useList) are only CALLED, never edited.

5.2 A real bug was found and fixed. There are TWO projectDetails links in
    ProjectList.tsx. An earlier attempt updated only the Name-column link and
    left the health-popover evidence link passing the raw id — which would have
    broken "click a failing resource" navigation. Both now go through one helper.

5.3 A routing footgun was avoided. Making id = `cluster/namespace` puts a "/"
    inside a single :name route parameter, which is fragile through generatePath
    and on hard reload (404 or %252F double-encoding). The route was therefore
    changed to TWO EXPLICIT SEGMENTS: /project/:cluster/:name.

5.4 The logic was validated against the REAL algorithm. localHealth.ts (1305
    lines) was executed verbatim (only its two import lines swapped) against
    generic fake clusters: 40 scenario assertions, 40 passed, 0 failed —
    including same-namespace-in-two-clusters producing two rows with DIFFERENT
    health (masking fixed), route round-trips resolving to exactly one instance
    (including a dotted cluster name), unreachable-cluster isolation, all health
    states, and non-health-bearing Job / Helm-hook-Pod behaviour.

5.5 The change was implemented and measured against a self-measured baseline.
    CRITICAL, MUST NOT BE GLOSSED OVER: this repository's test suite is ALREADY
    RED before any change. "All tests pass" is not achievable here. The correct
    bar is ZERO NEW FAILURES.
      BASELINE (clean): tests 280 failed | 3107 passed (3387); 10 failing files
                        typecheck 7 errors (6 localHealth.test.ts,
                        1 useLocalHealthItems.test.tsx)
                        pre-existing failures include App/Home/ClusterTable (2),
                        Sidebar (4), lib/k8s/index (12), storybook (249)
      AFTER:            tests 279 failed | 3111 passed (3390); SAME 10 failing
                        files; typecheck SAME 7 errors (0 new)
                        (+3 new tests; storybook 249->248, incidental/likely flaky)
    The 7 typecheck errors were PROVEN pre-existing by stashing the change and
    re-running the typecheck on clean code. ESLint, Prettier and the production
    build all pass.
    One failure WAS introduced during the work (a test asserting the old id
    format) and was found and fixed rather than hidden.

5.6 What repeatedly blocked us, and why it is NOT a code problem: live browser
    verification never succeeded because the environment running the app could
    not read the cluster — the namespace API returned 403 Forbidden, cluster
    navigation hit a login redirect and 502, and local clusters were unreachable.
    UI rows kept appearing from CACHED state, which is not proof. Separately,
    `oc auth can-i list namespaces` returned "yes" from the developer's own
    laptop, so the account HAS the permission; the credential used by the app's
    environment is simply not the same working one. An earlier claim that "the
    token is stale" was an assumption stated as fact and was wrong — the only
    hard evidence is the 403 itself.

8. KNOWN BEHAVIOUR CHANGES (state them; do not hide them)
--------------------------------------------------------------------------------
- Old bookmarks of the form /project/<namespace> no longer resolve. The details
  URL is now /project/<cluster>/<namespace>.
- The Applications list now counts INSTANCES, not logical applications, so it is
  longer on multi-cluster fleets. The namespace filter still works; adding a
  cluster filter is a sensible follow-up.
- There is no fleet-wide rollup row (see section 4).
- Unchanged: the health algorithm, the 60s polling refresh, and the
  Job/CronJob/HPA "Needs Attention" behaviour.
