--------------------------------------------------------------------------------
1. THE PROBLEM (why we are doing this)
--------------------------------------------------------------------------------
The Applications tab (route "/projects" -> components/project/ProjectList.tsx)
auto-discovers applications from namespaces: application name = namespace name.
Today discoverProjectsFromNamespaces() GROUPS BY NAMESPACE NAME, so a namespace
that exists in several clusters collapses into ONE row whose `clusters` array
holds every cluster. Health is then computed over the POOLED resources of all
those clusters via one worst-wins verdict (localHealth.ts / getLocalHealth).

Three real defects follow:
 (a) MASKING — healthy in cluster-A but one crashing pod in cluster-B reads as a
     single "Unhealthy" row with no way to see which cluster is at fault.
 (b) FALSE UNAVAILABLE — LocalHealthCell takes only the FIRST fetch error, so one
     unreachable cluster marks the whole application "Unavailable" even when the
     other clusters are fine.
 (c) NO ATTRIBUTION — LocalHealthEvidence carries kind/namespace/name but no
     cluster, so even the popover cannot say where a failing resource lives.

--------------------------------------------------------------------------------
2. THE GOAL
--------------------------------------------------------------------------------
One row per (cluster, namespace): every row is exactly ONE application instance
in ONE cluster and ONE namespace, with its OWN independently computed health.
A namespace present in three clusters becomes three rows.

Non-goal: do NOT change the health algorithm. localHealth.ts stays untouched —
once each row is scoped to a single cluster+namespace, getLocalHealth() already
describes exactly one instance.

3.1 frontend/src/components/project/ProjectList.tsx
  a) Discovery — replace the groupBy collapse with a flat map:
       const visible = namespaces.filter(
         n => n.metadata?.name && !isSystemNamespace(n.metadata.name)
       );
       return visible.map(({ metadata, cluster }) => ({
         id: `${cluster}/${metadata.name}`,
         namespaces: [metadata.name],
         clusters: [cluster],
       }));
     KEEP the `n.metadata?.name` guard (regression #5254) and the
     isSystemNamespace exclusion. Drop the now-unused `groupBy` lodash import
     (keep `uniq`, still used for the namespace filter options).
  b) Add an exported route-params helper:
       export function projectDetailsParams(project: ProjectDefinition) {
         return { cluster: project.clusters[0] ?? '', name: project.namespaces[0] ?? '' };
       }
  c) useProject(name) -> useProject(cluster, name); resolve with
       project.clusters[0] === cluster && project.namespaces[0] === name
     and fall back to { id: `${cluster}/${name}`, clusters: [], namespaces: [] }.
     Add `cluster` to the useMemo dependency array.
  d) BOTH projectDetails links must use the helper — this is the step that is
     easy to miss and silently breaks the popover:
       - the Name column cell (display the namespace, not the composite id), and
       - EvidenceRow inside the health popover (~line 445).
     Change EvidenceRow/EvidenceSection to take `project: ProjectDefinition`
     instead of `projectId: string`, and pass `params={projectDetailsParams(project)}`.
  e) Column: id 'clusters' / header t('Clusters') / clusters.join(', ')
     becomes id 'cluster' / header t('Cluster') / clusters[0] ?? ''.

4. KNOWN BEHAVIOUR CHANGES (state these, do not hide them)
--------------------------------------------------------------------------------
- Old bookmarks of the form /project/<namespace> no longer resolve; the details
  URL is now /project/<cluster>/<namespace>.
- The Applications row count now counts INSTANCES, not logical applications, so
  the list is longer on multi-cluster fleets. The namespace filter still works;
  consider adding a cluster filter as a follow-up.
- A namespace in N clusters yields N rows. There is no fleet-wide rollup row.
  (If a single "is this app OK everywhere?" line is wanted later, add a grouped
  parent row on top of these instance rows — additive, not a rewrite.)
