==============================================================================
1. WHAT P0 IS
==============================================================================
Goal (one line): the cluster status must be TRUTHFUL and resilient — a single
network blip must never show a false "Unavailable"/"Not reachable", while a
REAL auth error (401/403) must surface immediately.

P0 covers exactly two things:
  (A) The All Clusters tab status (GET /version poll + per-cluster auth poll
      via POST selfsubjectrulesreviews).
  (B) The ONE-SHOT auth check that runs when you click to open a cluster, and
      the screens it shows (ClusterAccessGate: checking / unreachable /
      expired / forbidden).

P0 does NOT cover (these are P1 — see Section 5):
  - Auto-recovery of the auth state AFTER you are already inside a cluster
    (confirmed: the inside-cluster check re-fires only on internal ROUTE
    CHANGE, i.e. navigating between pages like Namespaces/Nodes/Pods within
    the same cluster — each route change remounts the query component. It
    does NOT poll periodically while sitting still on one page.)
  - Live watch/WebSocket data freshness/reconnect.

3. HONEST STATUS — fully verified, not "code done + unit tested"
==============================================================================
The original version of this document claimed "code done + unit tested" as
sufficient. It was not. Four real defects shipped despite passing unit tests,
because the test suite's fake-timer config never faked `setInterval` — the
exact mechanism React Query uses to schedule `refetchInterval`. No existing
test could ever have observed real polling behavior. This was fixed (see
Section 4d) and is the single most important lesson from this verification
cycle.

Verified (both code-level AND live-cluster, real browser, real API responses):
  - Items 1-9 above: full live verification, evidence summarized in each row.
  - Backoff curve, keep-last-good, jitter spread, AuthRoute gate states: all
    confirmed via simulator (deterministic, fake-timer, real QueryClient) AND
    live capture (real cluster, real 401/403/502 responses).
  - The vitest fake-timer gap (Section 4d) is fixed; setInterval/clearInterval
    are now faked, and a regression baseline is recorded (3426 total tests,
    280 pre-existing failures unrelated to this work, confirmed unchanged
    before/after every fix via git-stash comparison).

Corrected from the original doc (see Section 4 for full stories):
  - Item 4(a) "logout feels slow" — investigated and found to be a NON-ISSUE.
  - Item 8 backoff — was masked by a real bug (Finding E, fixed) that made it
    LOOK broken in live testing; the underlying logic was always correct.
  - Item 10 — was never implemented as originally described; corrected and
    moved to P1.
  - A related caching issue (Finding G) was found and fixed: the inside-cluster
    auth check inherited a 3-minute cache from the global QueryClient default,
    meaning a revoked permission might not be detected for up to 3 minutes.
    Fixed to a 15-second override on that specific query only.
  - A diagnostic/observability issue (Finding F) was found and partially fixed:
    real fetch errors were being masked as a generic 502 with no visible cause.
    See Section 7 for the full two-part breakdown of what was fixed and what
    remains (moved to P1-3).

4. THE FINDINGS — full honest history
==============================================================================

--- 4(a). "Logout feels slow" — INVESTIGATED, CLOSED AS NON-ISSUE ---

The original doc theorized this could happen if logout doesn't return a clean
401/403 (e.g. a timeout instead), causing the poll to back off.

VERIFIED via a real `oc logout` against the live cluster, single continuous
browser script, listener instrumentation verified clean: the auth poll
returned a clean 403 in ~300-1150ms, and consecutive poll gaps stayed at
~10s afterward (no backoff). The theory was wrong, in the good direction —
this was never actually broken. No fix needed. Closed.

--- 4(b). Finding E: poll jitter caused unstable cadence (FIXED) ---

Root cause: `withJitter()` in resilience.ts returned a fresh `Math.random()`
value on EVERY call, and `refetchInterval` is a function React Query
re-evaluates on every render. Each time the returned interval value changed,
React Query tore down and restarted the poll timer (`clearInterval` +
`setInterval`). Live captures showed gaps up to 65s on a HEALTHY, all-success
cluster — impossible under the documented cap, and initially misdiagnosed as
several different, unrelated bugs (see Finding H below) before the true
mechanism was isolated.

Proven via simulator: with fake timers and `setInterval`/`clearInterval`
wrapped, 183 timers were created and 183 cleared, but ZERO ever fired to
completion — direct proof of the reset-loop.

FIX: added `withStableJitter(ms, key)` alongside the original `withJitter`
(unchanged, still used correctly for the open-gate retry delay, which
genuinely needs fresh randomness per attempt per standard "Full Jitter"
retry practice). The new function derives a deterministic offset from a
string hash of `key` (cluster name + query type), so the same cluster+query
always resolves to the same interval — stable across renders, but still
different across clusters (preserving item 9's anti-thundering-herd spread).

VERIFIED: simulator gaps became stable (18/18 in-band); 5 mock clusters kept
distinct offsets; the retry-delay path was confirmed to still use genuine
randomness (10 consecutive calls, 10 different values); live 180s capture on
the real healthy cluster showed all gaps in the 8.5-11.5s band; full
regression suite showed zero new failures (280/3426, unchanged via git-stash
comparison against the pre-fix state).

--- 4(c). Finding H (initially suspected) -> RETRACTED once Finding E was fixed ---

Before Finding E's fix, permanently-down clusters (minikube, docker-desktop,
always returning real 502s) were observed polling at a flat ~10s forever,
never backing off toward the documented 20s/30s cap — appearing to contradict
item 8.

After Finding E was fixed, the SAME live test was re-run: each cluster+query
combination settled at its own STABLE interval near the 30s cap (25.5s-34.5s,
i.e. exactly cap +/- 15% jitter). Directly inspecting the live
`consecutiveFailures` counter confirmed values of 10-11 for these clusters —
well past the point where `Math.min(base * failures, base * 3)` caps at
30000ms regardless of the exact counter value. The backoff logic was correct
the entire time; Finding E's timer-reset bug had been preventing it from ever
being observed correctly. Finding H is retracted — no separate defect existed.

--- 4(d). The vitest fake-timer gap (FIXED, test-infra only) ---

React Query schedules `refetchInterval` via `setInterval`. The project's
vitest config only faked `Date`/`setTimeout`/`clearTimeout` — `setInterval`
was never faked. This means NO test in the suite could ever have exercised
real polling behavior, at any point before this investigation. This is why
"unit tested" did not mean "polling verified" for this codebase.

FIX: added `setInterval`/`clearInterval` to the global `fakeTimers.toFake`
list in vitest config. Verified this did not silently break anything: full
suite re-run showed identical totals before/after — meaning no existing test
was exercising fake interval timing at all, confirming the coverage gap
rather than fixing a hidden failure.

--- 4(e). Finding G: 3-minute stale cache on the inside-cluster auth check (FIXED) ---

The global QueryClient default (`queryClient.ts`, upstream/unmodified,
`staleTime: 3 * 60_000`) is inherited by the one-shot AuthRoute query that
runs when opening a cluster. VERIFIED live (logged-in session, real 201
responses): navigating between 3 different internal routes (Namespaces,
Nodes, Advanced Search) within a 3-minute window reused the cached auth
result with ZERO new requests each time. If a permission were revoked in
that window, the app would not detect it until the cache expired — up to
3 minutes later.

Also discovered while investigating this: the inside-cluster auth check is
tied to the ROUTE (its query is keyed/remounted on `${routePath}-${cluster}`),
not to a timer — so it DOES refire on every internal navigation, just
subject to the 3-minute cache. This corrects the original, incomplete
understanding of item 10 (see Section 4(f)).

FIX: added `staleTime: 15_000` to ONLY this one query, in RouteSwitcher.tsx
(a fork-modified file — zero new merge risk; the global 3-minute default in
queryClient.ts, an upstream file, was left untouched).

Why 15s and not 0: live testing showed a user can hit 3 different internal
routes within ~4 seconds. staleTime:0 would fire a new request on EVERY
route change, multiplied across all concurrent users — real backend load
risk. 15s absorbs rapid navigation (proven: a 3-click burst within ~3 seconds
produced only 1 new request, not 3) while cutting the detection gap from
3 minutes to ~15-20 seconds (proven: waiting 20s+ before the next navigation
reliably triggered a fresh request).

VERIFIED: spaced navigation (20/25/30s apart) each triggered a fresh request;
rapid burst (3 clicks in ~3s) produced only 1 request; 20s wait produced a
fresh request; full regression suite unchanged (280/3426, same pre-existing
failures); scope check confirmed only this one query was affected — the
global default and all other queries (including the All Clusters polls)
remained on their original settings.

--- 4(f). Finding L / Item 10 correction ---

Original item 10 claimed: while sitting inside a cluster, a network blip
would be absorbed by keep-last-good logic and shown as a "Reconnecting..."
chip, escalating to the gate only after sustained failure — mirroring the
All Clusters page's behavior.

VERIFIED this does not exist: sitting still on ONE internal page for 60+
seconds produces exactly ONE auth request (at mount) and zero repeats — there
is no recurring poll to ever "blip."

Further verified: the auth check DOES refire, but only on internal ROUTE
CHANGE (navigating to a different page within the same cluster), because the
component holding the query is keyed on the route path and remounts on
navigation. This is different from a timer-based recurring check.

This corrects the record but is not a P0 defect — this document's own
Section 1 already excludes "auto-recovery of the auth state AFTER you are
already inside a cluster" from P0 scope. Item 10 as originally written
contradicted that stated scope. Moved to P1 (Section 5).

7. FINDING F — 502 MASKING (PARTIALLY FIXED — full two-part breakdown)
==============================================================================
In clusterRequests.ts, `clusterRequest` pre-initializes the response to a
generic 502 and only special-cased AbortError in its catch block, discarding
any other real error name/message (CORS block, DNS failure, connection
refused). Downstream code then fails to parse the empty 502 body as JSON,
producing `SyntaxError: Unexpected end of input`, observed repeatedly in live
console captures.

Confirmed this does NOT corrupt P0's decision logic: both a real 502 and a
masked-CORS-502 fall into the same "not 401/403 -> increment failures"
bucket, so backoff/keep-last-good behavior was never affected. This was
always a diagnostic/observability issue, not a functional P0 defect.

--- F Part 1 (FIXED): statusText now preserves the real cause ---

clusterRequest's catch block was updated:

    let response = new Response(undefined, { status: 502, statusText: 'Unreachable' });
    try {
      response = await fetch(url, requestData);
    } catch (err) {
      if (err instanceof Error) {
        if (err.name === 'AbortError') {
          response = new Response(undefined, { status: 408, statusText: 'Request timed-out' });
        } else {
          response = new Response(undefined, {
            status: 502,
            statusText: `Unreachable: ${err.name} - ${err.message}`,
          });
        }
      }
    }

For any non-abort error, the 502 response's statusText now reads
`Unreachable: {err.name} - {err.message}` instead of the bare word
"Unreachable". Status code contract unchanged (502 for non-abort, 408 for
AbortError). VERIFIED live: forced a genuine ERR_CONNECTION_REFUSED scenario,
confirmed statusText now carries "Unreachable: TypeError - Failed to fetch".
Regression suite unchanged (280/3426 pre-existing failures, nothing new
broken).

--- F Part 2 (FIXED): V1's parse-error console.error now prints the detail ---

The constructed `message` variable (carrying the new statusText detail) was
being built but never passed to the parse-error `console.error` call, so it
never actually reached the developer console despite Part 1's fix. Added
`message` as an argument to that console.error call. VERIFIED live: console
now shows "Unreachable: TypeError - Failed to fetch" instead of just the
generic parse error text. Regression suite unchanged.

--- Technical Details UI (no fix needed, verified working) ---

ClusterAccessGate's "Technical details" expandable section already read
`error.message` before this investigation began — the code was already
there, just never had rich data to display. VERIFIED live: after Parts 1 and
2's fixes, the expanded Technical Details now shows both "HTTP code: 502"
AND "Unreachable: TypeError - Failed to fetch" together, confirmed via
accessibility snapshot. No code change was needed in ClusterAccessGate.tsx
for this — the existing component simply started receiving richer data once
Part 1 was fixed.

--- F Part 3 (NOT FIXED, tracked as P1-3): V2 API path ignores statusText ---

A separate, independent API-calling system
(frontend/src/lib/k8s/api/v2/fetch.ts) constructs its own `ApiError` and
never reads `response.statusText` at all:

    throw new ApiError(maybeErrorMessage ?? 'Unreachable', { status: response.status });

For an empty 502 body, `maybeErrorMessage` is always undefined, so
`ApiError.message` is always the bare word "Unreachable" regardless of Part
1's fix. This is why `useSidebarItems.tsx`'s "Failed to fetch CRDs:
ApiError: Unreachable" console line does not improve, even after Parts 1
and 2 were fixed.

NOT fixed — deliberately deferred, larger scope than V1's fix. V2 likely has
significantly more callers than V1's single clusterRequests path, meaning a
bigger surface area for regressions. Moved to P1-3 (see Section 5).

Decision: do not patch V1 (Part 1/2) locally without evidence it was safe —
already done, verified, low risk, committed. Do not patch V2 without a
separate, dedicated investigation first — folded into the same upstream
inquiry as Part 1. An inquiry covering both the original masking behavior
(Part 1) and V2's gap (Part 3) was sent to upstream maintainers; awaiting
response.

9. TEST METHODOLOGY NOTES (for whoever verifies this next)
==============================================================================
- Fresh browser tab for every test; never `location.reload()` (causes request
  races that look identical to real bugs).
- Verify listener/instrumentation counts (via before/after delta where an
  absolute baseline isn't achievable) before trusting any capture.
- Cross-check captured records against console output; a mismatch invalidates
  the run.
- Only `document.visibilityState` matters for TanStack Query's focus manager;
  `document.hasFocus()` is not checked by the library and is not a valid gate.
- Prefer offline simulators (real QueryClient/QueryObserver + fake timers)
  over live browser automation for anything timing-related — simulators
  proved far more reliable throughout this investigation than repeated
  browser-automation attempts, which produced two fully retracted findings
  (J, K) due to tooling artifacts alone.
