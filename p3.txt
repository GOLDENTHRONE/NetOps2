==================================================
2. FIX #1 — NON-HEALTH-BEARING API ERRORS
==================================================

CURRENT PROBLEM:

An API error/observability gap from a non-health-bearing resource can currently cause the entire ApplicationHealth.status to become "unknown".

For example:

- Deployments are observable and healthy
- StatefulSets are observable and healthy
- Pods are observable and healthy
- LimitRange API returns 403

The application MUST NOT become Unknown just because LimitRange failed.

RULE:

Only observability gaps involving HEALTH_BEARING_KINDS may block a definitive application health calculation and force:

status = "unknown"

API failures for supporting/non-health-bearing resources must NOT override an otherwise determinable application health.

Examples of non-health-bearing failures:
- ConfigMap 403
- Secret 403
- Role 403
- RoleBinding 403
- ResourceQuota 403
- LimitRange 403
- NetworkPolicy 403
- Service 403
- Endpoints 403
- EndpointSlice 403
- HPA 403
- CronJob 403

These may be retained as non-blocking observability/informational gaps if the existing data model supports it, but they must not make the whole application Unknown.

However:

Pod API 403
Deployment API 403
StatefulSet API 403
DaemonSet API 403
Job API 403
PVC API 403

MUST still be capable of producing Unknown because these resources participate in health calculation.

Do not fake a health status when required health-bearing data cannot be observed.

==================================================
3. FIX #2 — JOB HEALTH SEMANTICS
==================================================

CURRENT PROBLEM:

The evaluator appears to treat:

status.failed > 0

as automatically Unhealthy.

That is incorrect because Kubernetes Jobs can fail one or more retry attempts and later successfully complete.

Example:

failed = 1
succeeded = 1
condition[type=Complete] = True

This Job is HEALTHY.

RULE:

Evaluate the Job's terminal state, not merely historical retry count.

A Job MUST be Healthy when:
- condition[type=Complete].status == "True"

OR, where appropriate according to the existing Kubernetes status model:
- succeeded > 0
- and there is no active terminal Failed condition indicating the Job ultimately failed

A Job MUST be Unhealthy when:
- condition[type=Failed].status == "True"
- and it has not successfully completed

Do NOT mark a completed Job Unhealthy just because:
status.failed > 0

Preserve the existing health semantics for active/running Jobs.

==================================================
4. FIX #3 — DUPLICATE FINDINGS / ROOT CAUSE
==================================================

CURRENT PROBLEM:

A failing Pod can produce a concrete finding such as:

Pod X — CrashLoopBackOff

while its parent Deployment also produces:

Deployment — 0/1 replicas available

This creates duplicate findings for the same underlying problem.

RULE:

If an owned Pod already produces a concrete error finding for its workload, suppress the generic parent replica-shortage finding for that same Deployment/StatefulSet.

Examples of concrete Pod failures include:
- CrashLoopBackOff
- OOMKilled
- ImagePullBackOff
- ErrImagePull
- ContainerConfigError
- other existing authoritative Pod failure reasons already supported by the evaluator

Keep the concrete root-cause Pod finding.

Suppress only the redundant parent warning.

Do NOT suppress the parent finding if there is no concrete child error explaining the shortage.

Example:

Case A:
Pod → CrashLoopBackOff
Deployment → 0/1 available

Expected:
1 finding:
Pod → CrashLoopBackOff

NOT:
Pod → CrashLoopBackOff
Deployment → 0/1 available

Case B:
Deployment → 0/1 available
No failing Pod finding

Expected:
Deployment replica-shortage finding remains.
