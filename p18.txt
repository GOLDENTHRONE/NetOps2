HOW THIS WORKS (since the cluster is on YOUR machine, not mine)
--------------------------------------------------------------
I cannot reach your live OCP cluster from here, so the loop is:
  1) I added temporary, tagged debug logs at the suspicious points in the code
     (all gated OFF by default; they print only status codes / booleans / cluster
     names — NEVER tokens or header values).
  2) YOU pull GT_D_V1, run localhost:3000 against the live cluster, turn the logs
     ON, reproduce the logout/login, and capture Console + Network + DOM.
  3) YOU paste the captured output back (PART 5). I read it and pinpoint the fix.

The logs are the "inside view" (what the frontend saw); the Network tab is the
"outside truth" (what the server actually returned + which credentials were sent);
together they localize the bug precisely.

-------------------------------------------------------------------------------
 WHERE THE LOGS ARE (what each tag means)
-------------------------------------------------------------------------------
Helper: frontend/src/lib/gtDebug.ts  (grep "gtDebug" to find/remove all of them)

  [GT-DEBUG] clusterRequest          — EVERY cluster API call (the choke point).
       Fields: cluster, path, method, status, ok, authHeaderPresent,
               autoLogoutOnAuthError.
       -> This is the decisive one: the live HTTP status of /version and
          /selfsubjectrulesreviews, and whether a JS-attached token was sent.
  [GT-DEBUG] clusterRequest.autoLogout — a 401 with a token header triggered logout.
  [GT-DEBUG] useClustersVersion.map   — per cluster, per poll cycle: isPending,
       isFetching, rawErrorStatus, hasData, shownErrorStatus, consecutiveFailures.
  [GT-DEBUG] useClustersAuth.map      — per cluster: isPending, isFetching,
       rawErrorStatus, shownErrorStatus.
  [GT-DEBUG] rowStatus                — the FINAL status text the table renders,
       with versionErrorStatus / authTracked / authErrorStatus that produced it.
  [GT-DEBUG] watch.close              — a P1 watch dropped/handshake-failed
       (cluster, code, reason, attempt).

Reading them together tells you the whole chain for one cluster:
  clusterRequest(status) -> useClusters*.map(shownErrorStatus) -> rowStatus(text)

  Q2. When that selfsubjectrulesreviews line appears LIVE, what is its status?

stops polling an errored query" — I reproduced the exact useQueries + growing

above tells us the real cause.

 HOW I WILL READ IT (so you know what we're proving)
-------------------------------------------------------------------------------
• LIVE status 401/403 AND reload status 200, with the SAME request headers both
  times  => backend session/token caching. The frontend is correct (it faithfully
  showed each result). Fix belongs in the Headlamp/NetOps2 BACKEND (rebuild the
  cluster client when the token changes). Not fixable in this frontend repo.

• LIVE status 401/403 AND reload 200, but request headers DIFFER (e.g. an
  Authorization/KUBECONFIG present on reload but stale/missing live)  => the
  FRONTEND is sending a stale credential. Fixable here (refresh the credential /
  invalidate the readiness queries on token change).

• LIVE clusterRequest already 200 but rowStatus still shows the old text  =>
  FRONTEND render/propagation bug. Fixable here (I'll dig the hooks->table chain).

• clusterRequest for the OCP cluster STOPS appearing after re-login (no ~10s
  lines)  => the poll stopped (background pause / observer gc). Different fix.

 NOTES
-------------------------------------------------------------------------------
- The logs are TEMPORARY and OFF unless window.__GT_DEBUG__ === true. To remove
  them entirely later: delete frontend/src/lib/gtDebug.ts and every line matching
