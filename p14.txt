WHAT WE ARE VERIFYING (plain terms)
  A "watch" is an open connection (WebSocket) that pushes live updates for lists
  and detail pages. In this app there are two generations:
   - v1 (logs/exec/metrics streaming) ALREADY reconnects — not our concern here.
   - v2 (resource LISTS + detail pages) is the one with NO reconnect. When its
     socket drops, the app does not redial and does not fall back to asking, so
     the screen silently freezes (stale). We want the REAL numbers for v2, and
     to see whether the backend ever returns HTTP 410 ("resume point too old").

CODE FACTS TO CONFIRM (read-only, quote file:line)
  V1  webSocket.ts openWebSocket registers ONLY 'message' and 'error' on the
      socket — NO 'close' handler, NO reconnect.            [webSocket.ts:129,140]
  V2  the v2 watch is used by BOTH lists and single-object detail pages:
      useKubeObjectList.ts (legacy useWebSockets) + hooks.ts (useWebSockets).
                                        [useKubeObjectList.ts:552, hooks.ts:223]
  V3  watch and periodic refetch are mutually exclusive:
      shouldWatch = watch && !refetchInterval && ...        [useKubeObjectList.ts:784]
  V4  v1 streaming DOES reconnect (for contrast): onclose -> setTimeout(connect,
      3000) when reconnectOnFailure.                         [streamingApi.ts ~362]
  Report TRUE/FALSE for each with the snippet.
