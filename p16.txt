p16 — LOCAL POD-FETCH PLUGIN FOR APPLICATIONS TAB HEALTH
Target branch: GT_D_V1  (do NOT push upstream; do NOT open a PR to kubernetes-sigs/headlamp)
Scope:        Add Pod to the resources fetched per project so that the
              custom health column introduced in p15 can evaluate Pod-level
              signals directly (CrashLoopBackOff, ImagePullBackOff, Failed,
              stuck Pending, Ready=False on Running).
Depends on:   p15.txt on this same branch (custom localHealth column).
================================================================================

WHY THIS EXISTS
--------------------------------------------------------------------------------
p15 introduced a local "Status" column driven by getLocalHealth() with rich
per-kind rules. The Pod rules in that spec are correct, but they never
actually fire, because the Applications tab's fetch list
(defaultApiResources in frontend/src/components/project/projectUtils.ts) does
NOT include Pod. useProjectItems() therefore never returns any Pod objects.

Consequences observed in p15 alone:
  - CrashLoopBackOff / ImagePullBackOff / Failed pods are only caught
    INDIRECTLY, via Deployment/RS/SS/DS readyReplicas dropping.
  - Bare Pods (no owning workload — e.g. `kubectl run …`) are completely
    invisible: no controller reports a low readyReplicas for them.
  - Pods stuck in Pending because of unschedulable requests/quota also often
    slip through when the owning ReplicaSet has not yet updated its status.

p16 fixes this WITHOUT editing projectUtils.ts (or any other shared file) by
introducing a small local Headlamp plugin that calls the already-existing
plugin API `registerProjectApiResource({ kind: 'Pod', ... })`. Redux state
`state.projects.apiResources` is merged with the built-in
`defaultApiResources` inside `useProjectResources.ts:39`
(`uniqBy([...defaultApiResources, ...pluginApiResources], ...)`), so the
project fetch will start including Pod lists per namespace and per cluster
automatically, without any change to shared code.

   * Local plugin (fork-only, GT_D_V1 branch).
   * Purpose: make Pod objects available to the Applications tab health column.
   * Related spec files on the same branch: p15.txt (health column), p16.txt (this).
   *
   * Effect: useProjectResources.ts merges plugin-registered resources with
   * defaultApiResources via uniqBy(..., apiResourceId). Registering Pod here
   * makes each Application (namespace) fetch its Pod list too, feeding those
   * Pod objects into the items[] passed to getLocalHealth() in p15's column.
   */
  import { registerProjectApiResource } from '@kinvolk/headlamp-plugin/lib';

  registerProjectApiResource({
    apiVersion: 'v1',
    version: 'v1',
    pluralName: 'pods',
    singularName: 'pod',
    kind: 'Pod',
    isNamespaced: true,
  });

  // Intentionally no default export — this plugin exists only for its
  // side-effect registration call above.

HOW p16 PLUGS INTO p15 (verify the seam)
--------------------------------------------------------------------------------
1. p15 added a new column driven by `getLocalHealth(useProjectItems(project))`.
2. `useProjectItems` -> `useProjectResources` -> fetch list built from
   `uniqBy([...defaultApiResources, ...pluginApiResources], apiResourceId)`.
3. With p16's plugin loaded, `pluginApiResources` includes the Pod entry.
4. `apiResourceId(Pod-from-defaults?) is not present` — Pod is not in
   defaults — so uniqBy keeps the plugin's Pod entry. Fetch list length goes
   from 19 to 20.
5. useKubeLists issues one extra GET per cluster:
     GET /clusters/<cluster>/api/v1/namespaces/<ns>/pods
6. Returned Pod objects flow into the same items[] passed to
   getLocalHealth(); the Pod-specific rules in p15.txt now start matching.

NO edit is needed to p15's files to make p16 take effect. Loading the plugin
is enough.


LOADING THE PLUGIN (dev + prod)
--------------------------------------------------------------------------------
Dev (Headlamp desktop / frontend dev server):
  1) cd plugins/local/pod-project-resource
  2) npm install
  3) npm run start   # serves the plugin build on the default plugin dev port
  4) Point Headlamp's plugins path to a folder containing this plugin's
     `dist/main.js` — the standard headlamp-plugin dev flow does this
     automatically when `start` is running.

Prod / packaged Headlamp:
  1) npm run build in the plugin folder → produces `dist/main.js`.
  2) Copy the plugin folder (or just `dist/`) into Headlamp's plugin
     directory (`~/.config/Headlamp/plugins/pod-project-resource/` on Linux,
     or the platform equivalent), OR mount it via the same mechanism the
     team already uses to ship internal plugins (kept out of this spec —
     use whatever the deployment pipeline uses today).
  3) Restart Headlamp; the plugin registers Pod at boot; the Applications
     tab health column starts seeing Pods on next refresh.
