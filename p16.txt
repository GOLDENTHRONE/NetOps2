-------------------------------------------------------------------------------
 GLOSSARY (plain)
-------------------------------------------------------------------------------
- watch / WebSocket (WS): the live phone line to the cluster. Live updates arrive
  on it. This is what P1 hardens.
- reconnect: when the line drops, redial automatically (with growing waits).
- resourceVersion (RV): a bookmark of "how far I've read". The watch resumes from
  it. If it is too old the server replies 410 Gone (Expired).
- 410 re-list: on a 410, throw away the old bookmark and fetch a fresh full list,
  then watch again.
- freshness chip: a small "Reconnecting live updates…" pill that appears while a
  watch is down, so the user knows data may be briefly behind.
- multiplexer: an alternative "one shared line for everything" transport. In this
  build it is OFF by default (see Scenario S10). P1 lives on the default path.

-------------------------------------------------------------------------------
Active watch path (default build):
  KubeObject.useList  -> useKubeObjectList (v2) -> useWatchKubeObjectListsLegacy
    -> useWebSockets  (src/lib/k8s/api/v2/webSocket.ts)
  KubeObject.useGet   -> useKubeObject (v2, src/lib/k8s/api/v2/hooks.ts)
    -> useWebSockets (+ useWebSocket multiplexer hook, gated OFF)

Config knobs (src/lib/resilience.ts), all env-overridable:
  WATCH_RECONNECT            = true      (REACT_APP_WATCH_RECONNECT)
  WATCH_RECONNECT_BASE_MS    = 1000      (REACT_APP_WATCH_RECONNECT_BASE_MS)
  WATCH_RECONNECT_CAP_MS     = 30000     (REACT_APP_WATCH_RECONNECT_CAP_MS)
  WATCH_FALLBACK_REFETCH_MS  = 90000     (REACT_APP_WATCH_FALLBACK_REFETCH_MS, 0=off)
  POLL_JITTER_PCT            = 0.15      (±15% jitter on the above)
  KEEP_LAST_GOOD             = true      (P0 auth-gate keep-last-good)
  STATUS_FAIL_THRESHOLD      = 2         (P0 blips before the gate)
  AUTH_TIMEOUT_MS            = 15000     (P0 auth probe timeout)

Reconnect mechanics (webSocket.ts):
  - connectionKey = cluster + url ; the url embeds `watch=1&resourceVersion=<rv>`.
  - On a real (unexpected) socket 'close', scheduleReconnect() runs with
    exponential backoff: delay = min(1000 * 2^attempt, 30000), ± jitter.
  - Backoff + "live" state are reset on the socket's real 'open' event (not
    when the open() promise resolves) — a socket that dies before establishing
    keeps backing off instead of hot-looping ~1s.
  - An intentional close (component unmount / superseded) does NOT reconnect.
  - watchStates drives useAnyWatchReconnecting() -> the freshness chip.

410 / ERROR handling:
  - List (useKubeObjectList legacy onMessage AND multiplexed handleUpdate):
      if update.type === 'ERROR' -> client.invalidateQueries(queryKey)  (re-list)
  - Detail (hooks.ts handleMessage): ERROR -> invalidateQueries (re-fetch object)
  - KubeList.applyUpdate never clobbers metadata.resourceVersion to undefined.

BOOKMARK handling (defensive; we do NOT request allowWatchBookmarks):
  - KubeListUpdateEvent type includes 'BOOKMARK'.
  - List: KubeList.applyUpdate case 'BOOKMARK' -> advance RV only, no item change,
    no "Unknown update type" error.
  - Detail: hooks.ts handleMessage returns early on BOOKMARK (never overwrites the
    object with the near-empty bookmark payload -> would blank the detail page).

Freshness chip (P1): src/components/cluster/WatchFreshnessChip.tsx
  - Text: "Reconnecting live updates…"  (role="status", aria-live="polite")
  - Position: fixed, BOTTOM-LEFT. Mounted in Layout.tsx after <TopBar/>.
Auth-gate chip (P0): src/components/cluster/ReconnectingChip.tsx
  - Text: "Reconnecting…"  Position: fixed, BOTTOM-RIGHT. In RouteSwitcher.tsx.

 PART D — SCENARIO TESTS (the core of P1)
===============================================================================

--- S1: single drop -> auto-reconnect + freshness chip -------------------------
Goal: a dropped watch redials and the user is told, then it clears.
DO:
  1. Stay on the watching list view from PART C.
  2. DevTools -> NETWORK -> Throttling dropdown -> select "Offline".
  3. Watch for ~2 seconds.
LOOK:
  - CONSOLE: a WebSocket error/close is logged (e.g. "WebSocket error:").
  - DOM: within ~1–2s the "Reconnecting live updates…" chip appears BOTTOM-LEFT
    (run the B3 one-liner, or just look). role="status".
  - NETWORK (WS): the old WS shows closed.
THEN:
  4. Throttling dropdown -> back to "No throttling" (online).
LOOK:
  - NETWORK (WS): a NEW WS opens to the same watch URL (resourceVersion present).
  - DOM: the chip DISAPPEARS shortly after the new socket opens.
  - The list resumes updating (make a change with kubectl to confirm live events).
PASS: chip showed during outage, a new WS opened on recovery, chip cleared, data live.
FAIL: no new WS after online (silent stale); chip never showed; chip stuck on after
      recovery; page threw / went blank.

--- S2: repeated drops -> exponential backoff (no storm) ------------------------
Goal: repeated failures back off (~1s, 2s, 4s, …), not a hot loop.
DO:
  1. Set Throttling -> "Offline" and LEAVE it offline for ~40 seconds.
LOOK (NETWORK WS, Preserve log ON): note the timestamps of successive WS connect
  attempts. Gaps should GROW roughly: ~1s, ~2s, ~4s, ~8s, ~16s, ~30s (±15% jitter),
  then stay capped near 30s.
  CONSOLE: repeated connect failures, but NOT dozens per second.
PASS: growing gaps, capped ~30s, no tight (<1s) retry storm.
FAIL: attempts every ~1s forever (no backoff); or attempts stop entirely before
      you go back online (gave up — should keep trying while subscribed).
THEN: go online -> a WS opens, chip clears (as S1).

--- S3: long outage -> backoff cap holds; recovers cleanly ---------------------
DO: from S2 still offline near the 30s cap, wait ~30 more seconds, then go online.
LOOK: attempts stayed ~30s apart (not longer, not shorter); on online, ONE new WS
  opens promptly; chip clears; exactly one live socket for the view (no duplicates
  in NETWORK WS that stay "pending"/open).
PASS: single clean recovery, no leaked/duplicate sockets.

--- S4: recovery correctness (data not just "connected") -----------------------
DO: after recovery, use kubectl to add/delete an item in the watched namespace.
LOOK: the list reflects the change within ~1–2s (live), without a manual refresh.
PASS: post-reconnect events actually update the DOM list.
FAIL: socket open but list frozen (connected-but-not-live).

--- S5: safety-net refetch on a quiet/silently-dead socket ---------------------
Goal: even if a socket dies WITHOUT a close event, the list still refreshes.
NOTE (honest limit): you cannot easily force a "silently dead" socket from
  DevTools. Instead observe the periodic safety-net refetch on a QUIET list.
DO:
  1. Open a watching list that changes rarely (a small, stable namespace).
  2. Do nothing for ~2 minutes. Keep NETWORK "Fetch/XHR" visible, Preserve log ON.
LOOK: roughly every ~90s (±15% -> ~76–104s) a background LIST GET fires for that
  resource (same list URL, refetch). This is watchFallbackRefetchInterval.
PASS: a periodic ~90s list refetch is visible while watching.
FAIL: no background refetch ever (safety net off when it should be on).
EDGE: if the list is PAGINATED (you clicked "load more" / a `continue` token is in
  play), the safety-net refetch is intentionally SUPPRESSED (it would reset your
  pages). Verify: on a paginated list, the ~90s refetch does NOT fire. PASS = suppressed.

--- S6: unsubscribe mid-reconnect -> loop stops, no leak -----------------------
Goal: leaving the page while reconnecting must cancel the redial (no zombie loop).
DO:
  1. On a watching list, set Throttling "Offline" (chip appears, backoff running).
  2. While still offline, NAVIGATE AWAY (open a different resource / route).
LOOK:
  - NETWORK (WS): no further connect attempts for the OLD list URL after navigation.
  - CONSOLE: the retry log for the old URL stops.
  - DOM: chip clears once nothing is reconnecting (if the new page is healthy).
THEN: go online. Confirm the OLD list URL never reconnects (only the new page's WS).
PASS: reconnect loop for the abandoned view stops; no leaked socket/timer.
FAIL: old URL keeps retrying after you left; chip stuck; two sockets for one view.

--- S7: 410 Gone -> fresh re-list (not swallowed into stale) --------------------
Goal: a 410 on the watch triggers a fresh LIST GET, not permanent staleness.
NOTE (honest limit): forcing a real 410 on a healthy cluster is hard (RV must
  age past the server's history window, ~5 min of churn). Two options:
  Option A (best-effort real): put the laptop/tab to sleep or Offline for 10–15
    min on a BUSY namespace, then resume. On resume the watch tries to resume from
    the now-too-old RV.
  Option B (trust the unit tests): W7 in the p1-sim and KubeList.test.ts already
    prove ERROR -> re-list + RV preserved.
LOOK (if you reproduce it):
  - NETWORK (WS Frames): an event with type "ERROR" whose object is a Status with
    code 410 / reason "Expired".
  - NETWORK (Fetch/XHR): immediately after, a FRESH list GET fires (the re-list).
  - DOM: the list repopulates and resumes live updates (not frozen).
PASS: 410 -> fresh GET -> live again. FAIL: after a 410 the list freezes and only
  the WS keeps reconnecting in a loop (the exact bug P1 fixes).

--- S8: detail (single object) view during a drop; BOOKMARK safety --------------
Goal: the detail page reconnects and is never blanked by a stray BOOKMARK.
DO:
  1. Open a single resource's DETAIL page (e.g. one Deployment).
  2. NETWORK (WS): confirm a watch with fieldSelector=metadata.name=<name>.
  3. Throttling "Offline" ~2s then online (as S1).
LOOK:
  - The detail page reconnects; fields stay populated; on recovery, edits via
    kubectl (e.g. scale replicas) reflect live.
  - The page NEVER flashes blank/empty during reconnect.
BOOKMARK note (honest limit): we do not request bookmarks, so you likely won't see
  a BOOKMARK frame. The defensive guard (hooks.ts returns early on BOOKMARK;
  KubeList advances RV only) is proven by unit tests. If your cluster/proxy DOES
  emit BOOKMARK frames, confirm the detail page does not blank and the list logs no
  "Unknown update type".
PASS: detail reconnects, stays populated, updates live. FAIL: blank flash, frozen
  fields, or console "Unknown update type" spam.

--- S9: P0 auth-gate — blip keeps last-good; 401/403 gates immediately ----------
Goal: confirm P0 still holds (a single blip must not destroy a healthy view), and
  P1's chip (bottom-left) does not collide with P0's chip (bottom-right).
DO (blip): open a cluster view successfully, then Throttling "Offline" briefly.
LOOK: the page CONTENT stays (last-known-good); a "Reconnecting…" chip appears
  BOTTOM-RIGHT (P0). It only turns into the full access gate after
  STATUS_FAIL_THRESHOLD (2) consecutive failures. Go online -> chip clears.
DO (real auth): if you can, hit a cluster/namespace you are NOT authorized for
  (or revoke access), forcing a 401/403.
LOOK: 401/403 is surfaced IMMEDIATELY (no keep-last-good, no debounce) — the gate
  appears at once. PASS = blips debounced/kept, but 401/403 immediate.
COLLISION CHECK: if both a watch drop and an auth recheck happen together, the P1
  chip (bottom-left) and P0 chip (bottom-right) sit in different corners and do not
  overlap.

--- S10: multiplexer OFF confirmation (and the ON caveat) -----------------------
DO (default build): NETWORK (WS) across the whole session — confirm there is NO
  connection to `.../wsMultiplexer`; only per-resource `?watch=1` sockets.
PASS: no wsMultiplexer; P1 default-path behavior (S1–S9) applies.
CAVEAT (do NOT do unless you specifically want to test the flag): if you run with
  REACT_APP_ENABLE_WEBSOCKET_MULTIPLEXER=true, the transport switches to a single
  wsMultiplexer socket. On THAT path 410 re-list still works, BUT auto-reconnect is
  NOT implemented (see the NOTE in multiplexer.ts: handleWebSocketClose only flags
  isReconnecting, never redials). So S1/S2/S3/S6 would FAIL by design there. This is
  documented, intentional, and out of P1 scope — the flag ships OFF.

--- S11: rollback flags actually roll back -------------------------------------
Goal: prove the resilience is config-gated (safe kill switch).
DO: run with REACT_APP_WATCH_RECONNECT=false (rebuild/restart), repeat S1.
LOOK: after a drop, NO reconnect fires and NO chip shows (old behavior restored).
PASS: flag off => pre-P1 behavior. Set it back to default (true) afterwards.
(Optional) REACT_APP_WATCH_FALLBACK_REFETCH_MS=0 => S5 periodic refetch stops.
