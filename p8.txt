# 4. DISTINGUISH HEALTH, SUPPORTING, INFORMATIONAL AND DIAGNOSTIC DATA

Be extremely strict about semantic classification.

For every resource involved, explicitly determine:

1. Is it HEALTH-BEARING?
   - Can it vote on application health?
   - Can it make the application Healthy/Degraded/Unhealthy?

2. Is it SUPPORTING?
   - Is it displayed as supporting context?
   - Does it participate in health voting?

3. Is it INFORMATIONAL?
   - Is it merely an existence/status/count?
   - Must it never affect application health?

4. Is it DIAGNOSTIC?
   - Is it evidence that helps explain a problem?
   - Does it explicitly vote on health?
   - By default: NO.

Diagnostic evidence must NEVER accidentally become a health vote.

---

# 5. HEALTH STATE MUST REMAIN SEPARATE FROM DIAGNOSIS

Never mix these concepts.

HEALTH:
- Healthy
- Degraded
- Unhealthy
- Unknown
- existing health states/counts

DIAGNOSIS:
- explanatory/correlational evidence,
- suspected dependency relationship,
- missing dependency,
- service readiness evidence,
- correlated Pod failure,
- PVC-related evidence,
- quota-related evidence, etc.

A diagnosis:
- MUST NOT vote,
- MUST NOT change application state,
- MUST NOT participate in worst-of-roots,
- MUST NOT be counted as another health failure,
- MUST NOT cause duplicate health votes.

Diagnosis is evidence, not health state.

# 15. BE VERY CRITICAL ABOUT SEMANTICS

Do not accept an implementation merely because TypeScript compiles or tests pass.

Challenge assumptions.

For every proposed condition ask:

"Does this represent actual Kubernetes/application health, or merely evidence/information?"

Examples:

A missing ConfigMap alone does NOT automatically mean application unhealthy.

A missing Secret alone does NOT automatically mean application unhealthy.

A Pending PVC alone does NOT automatically mean application unhealthy if PVC is informational under the agreed model.

A quota existing alone does NOT mean application unhealthy.

A Service having zero ready endpoints can be diagnostic only when there is a valid selector → in-scope Pod relationship and authoritative readiness evidence.

A diagnosis must not create a second health vote.

Do not infer causality when we only have correlation.

Use wording such as:
"correlated with"
"referenced by"
"associated with"
"evidence indicates"

rather than claiming:
"caused by"

unless the repository actually provides enough evidence to establish causality.

# 17. SERVICE READINESS DIAGNOSIS MUST BE CONSERVATIVE

Use selector semantics.

Only consider a Service when:
- Service selector matches in-scope Pod labels,
- matching Pods exist,
- authoritative endpoint data is already fetched,
- ready endpoints are zero.

Prefer EndpointSlice readiness if already available.

Use Endpoints only as the agreed fallback if EndpointSlice is unavailable.

Do not diagnose a Service merely because:
- it exists,
- it has no selector,
- no matching Pods exist,
- endpoint data was not fetched.

No matching Pod = unrelated/informational, not a health failure.
