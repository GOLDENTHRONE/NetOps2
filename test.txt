Why status is Unhealthy
-----------------------
Frontend uses worst-status wins:
- any error -> Unhealthy
- no errors and any warning -> Degraded
- no errors/warnings and at least one runnable workload -> Healthy
- resources exist but no runnable workload -> Passive
- no resources -> No Resources
- fetch error -> Unavailable

This app has 3 Job errors. That makes final status Unhealthy even though many other resources may be healthy.

Important: there is no separate backend health API for this column. Health is computed in frontend from Kubernetes API list responses proxied by backend.

End-to-end flow
----------------
1. User opens Applications tab: /#/projects.

2. Frontend discovers applications from namespaces.
   Code path:
   - ProjectList.tsx -> useProjects()
   - Namespace.useList({ clusters })
   - discoverProjectsFromNamespaces(namespaces)
   - system namespaces filtered by isSystemNamespace()

   Application identity rule:
   - each visible namespace becomes one application
   - application name = namespace name
   - same namespace name across clusters collapses into one application row

   For BGW 0013C:
   - namespace wnv7a0vbgw0013c becomes application wnv7a0vbgw0013c
   - cluster list contains default--api-wnv7a0-wnvlil-itn-3pc-att-com:6443--at9306

3. Frontend loads Resources column.
   Code path:
   - ProjectList.tsx Resources cell
   - useProjectItems(project, { disableWatch: true })
   - useKubeLists(defaultApiResources + pluginApiResources, project.clusters, 1000, 60000, project.namespaces)

   Behavior:
   - max 1000 items per resource kind
   - polling interval 60000 ms
   - watch disabled for Applications list
   - result item arrays flatten into one list
   - current row shows 845 total resources

4. Frontend loads Status column.
   Code path:
   - ProjectList.tsx LocalHealthCell
   - useLocalHealthItems(project)
   - shared = useProjectItems(project, { disableWatch: true })
   - podList = useKubeLists([Pod], project.clusters, 1000, 60000, project.namespaces)
   - items = shared.items + podList.items
   - getLocalHealth(items)

   Important local behavior:
   - Pods are fetched only for Status column.
   - Pod fetch does not mutate Redux project resources.
   - Pod fetch does not change Resources column, ProjectDetails, ResourceMap, backend, or plugins.

5. Backend receives frontend cluster API requests.
   Frontend call shape:
   http://localhost:4466/clusters/{clusterName}/{kubernetesApiPath}

   Backend route:
   /clusters/{clusterName}/{api:.*}

   Backend code path:
   - headlamp.go -> handleClusterAPI()
   - router.PathPrefix('/clusters/{clusterName}/{api:.*}')
   - auth.NewBackendTokenMiddleware(...)
   - clusterRequestHandler()
   - getContextKeyForRequest()
   - getContextWithWebSocketFallback()
   - kContext.ProxyRequest(w, r)

   Backend processing:
   - validates backend token/cookie middleware
   - finds cluster context from kubeconfig store
   - maps {clusterName} to real Kubernetes API server URL
   - rewrites request URL host/scheme/path to target cluster server
   - attaches Kubernetes Authorization bearer token when available
   - proxies response from Kubernetes API server back to frontend

6. Frontend parses Kubernetes list responses.
   Code path:
   - useKubeObjectList.ts -> kubeObjectListQuery()
   - clusterFetch(path, { cluster })
   - response.json()
   - list.items mapped into KubeObject classes
   - metadata.managedFields removed from list items to save memory
   - item.kind and item.apiVersion copied from list response
   - item.cluster set to cluster name

7. Health reducer calculates final status.
   Code path:
   - localHealth.ts -> getLocalHealth(items)
   - localGetItemStatus(item, allItems)
   - evidence sorted errors first, warnings second
   - reasons capped for summary, evidence popover shows object rows

Health rules by kind
--------------------
Pod:
- status.phase == Failed -> error, message Failed
- container waiting reason CrashLoopBackOff -> error
- container waiting reason ImagePullBackOff -> error
- container waiting reason ErrImagePull -> error
- container waiting reason CreateContainerConfigError -> error
- container waiting reason InvalidImageName -> error
- phase Running and Ready condition not True -> error, message Running but NotReady
- phase Pending older than 5 minutes -> error, message Pending > 5m
- phase Pending younger than/equal 5 minutes -> warning, message Pending
- otherwise success

Deployment, ReplicaSet, StatefulSet, DaemonSet:
- desired replicas == 0 -> success
- status.replicas == 0 and desired > 0 -> error, message 0/{desired} pods created
- ready replicas < desired replicas -> warning, message {ready}/{desired} ready
- otherwise success

Job:
- failed >= backoffLimit + 1 and succeeded == 0 -> error, message failed ({failed}/{backoffLimit + 1})
- otherwise success

For BGW 0013C failed jobs:
- observed message failed (1/1)
- means failed count reached retry threshold and succeeded is 0

CronJob:
- active runs > 1 when concurrencyPolicy == Forbid -> warning
- active runs > 5 otherwise -> warning
- otherwise success

PersistentVolumeClaim:
- phase Lost -> error
- phase Pending older than 2 minutes -> error, message Pending > 2m
- phase Pending younger than/equal 2 minutes -> warning
- otherwise success

Endpoints:
- if subsets contain addresses -> success
- if paired Service missing -> success
- if paired Service type ExternalName -> success
- if paired Service clusterIP == None -> success
- if paired Service has no selector -> success
- otherwise no addresses -> warning, message no endpoints

For BGW 0013C endpoint warnings:
- listed Endpoints objects have no usable endpoint addresses for selector-based Services
- frontend marks each as warning "no endpoints"

HorizontalPodAutoscaler:
- ScalingActive=False with reason not ScalingDisabled -> warning
- ScalingDisabled is treated as deliberate/off -> success
- otherwise success

Ingress:
- no loadBalancer.ingress address and object older than 5 minutes -> warning, message no address
- otherwise success

For BGW 0013C ingress warning:
- cbur-master-cbur-ingress has no load balancer address, so warning "no address"

Other fetched kinds:
- ConfigMap, Secret, Service, EndpointSlice, NetworkPolicy, Role, RoleBinding, ResourceQuota, LimitRange are success unless covered by specific rule elsewhere.

Unavailable flow
----------------
If any list fetch in useLocalHealthItems returns non-404 error:
- LocalHealthCell does not compute Healthy/Unhealthy from partial empty data.
- It calls getUnavailableHealth().
- Status becomes Unavailable.
- Popover shows cluster, HTTP code, and backend/API error message.

404 handling:
- useKubeLists ignores one 404 for a resource kind.
- Reason: some clusters do not support every optional API group/resource.
- 404 for one kind does not make whole application Unavailable.

Direct URL test note
--------------------
Manual browser fetches to /clusters/{cluster}/... can return 403 if missing Headlamp backend auth header.
Normal app calls use clusterFetch(), which adds Headlamp backend headers/cookies before backend proxy handles request.
