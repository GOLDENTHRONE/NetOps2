 5) THE TEST — do each step literally (GO -> CLICK -> LOOK -> VERIFY)
===============================================================================

--- STEP 1 — Baseline (PAGE-1) ------------------------------------------------
 GO:    http://localhost:3000/  (All Clusters).
 LOOK:  your cluster row STATUS cell = "Active" (or Ready/Reachable).
 CLICK: the status cell -> PAGE-2 popover opens -> note "last check" + interval (~10s).
        Close the popover.
 VERIFY console/network:
   api.response {path:"/version", status:200}  ==  Network /version Status 200
   table.version {rawErrorStatus:null, shownErrorStatus:null}
   row.status {text:"Active"}          ; NO chip.reconnecting ; NO red console errors.
 PASS if all match.

--- STEP 1b — Initial state must be truthful "Connecting…", not "⋯" (PAGE-1) ----
 GO:    hard-reload PAGE-1 (Ctrl+Shift+R) and watch the row the moment it appears.
 LOOK:  before the first /version answers, the row shows a spinner + "Connecting…"
        (NOT an ambiguous "⋯"), then resolves to Active/Ready once 200 arrives.
 VERIFY: row.status/table.version go from no-data -> shownErrorStatus:null -> "Active".
 PASS = a clear "Connecting…" then a real status; never stuck on "⋯".
 (If your build auto-connects all clusters, "Not connected" won't show; that's fine.)

--- STEP 2 — ONE blip must NOT break the row (PAGE-1 table keep-last-good) ------
 GO:    stay on PAGE-1, cluster showing Active.
 DO:    DevTools -> Network -> Throttling dropdown -> "Offline". Count ~3 seconds.
 LOOK:  the row STATUS must STAY "Active" (it must NOT flip to "Unavailable").
 DO:    Throttling -> "No throttling" (online again).
 VERIFY: api.response {status:502 or 408}  (a real blip — matches Network) ;
         table.version {rawErrorStatus:502/408, hasData:true, consecutiveFailures:1,
           blipSuppressed:true, shownErrorStatus:null} ;
         row.status {text:"Active"} throughout.
 PASS = row stayed Active on the single blip.   FAIL = it showed "Unavailable" at
        the first blip, or blipSuppressed:false while consecutiveFailures:1.

--- STEP 2b — SLOW-but-OK check must NOT false-fail (AUTH_TIMEOUT 5s->15s) ------
 Why: P0 raised the auth/version client timeout from 5s to 15s so a slow-but-
 successful check is not aborted into a false "not responding". This is a CORE P0
 fix and is different from STEP 2 (which is an instant network drop).
 GO:    PAGE-1, cluster Active.
 DO:    DevTools -> Network -> Throttling -> "Slow 3G" (or a custom profile that adds
        ~6-10s latency — i.e. SLOWER than the old 5s but FASTER than the new 15s).
 LOOK:  the request takes several seconds but eventually returns 200; the row stays
        "Active" (or briefly "Connecting…") and does NOT flip to "Unavailable".
 VERIFY: Network shows /version taking >5s then Status 200 ; api.response {status:200}
        (NOT 408) ; table.version {rawErrorStatus:null, shownErrorStatus:null}.
 PASS = a slow-but-successful check is tolerated (no false Unavailable / no 408 abort).
 FAIL = api.response {status:408} (aborted) or the row flips to "Unavailable" while
        the request would still have succeeded within 15s.
 THEN:  set Throttling back to "No throttling".

--- STEP 3 — SUSTAINED outage must honestly show "Unavailable" (PAGE-1) --------
 GO:    PAGE-1.
 DO:    Network -> "Offline" and KEEP it offline ~25-30s (let >=2 checks fail; watch
        api.response lines pile up).
 LOOK:  after the 2nd consecutive failure the row turns "Unavailable".
 CLICK: the status cell -> PAGE-2 popover -> it should also reflect the failure/timing.
 VERIFY: table.version {consecutiveFailures:>=2, blipSuppressed:false,
           shownErrorStatus:502/408} ; row.status {text:"Unavailable"}.
 PASS = Unavailable appears ONLY after the threshold (2), not on blip #1.
 THEN:  go back online; row returns to Active within a poll or two.

--- STEP 4 — real 401 (logout) must show IMMEDIATELY (PAGE-1) ------------------
 GO:    PAGE-1, cluster Active.
 ASK HUMAN: "Please LOG OUT of the OCP cluster now (or let the token expire), then
        reply 'logged out'." WAIT for reply. Do NOT reload.
 LOOK:  on the next check the row shows "Authentication required" (401 is not a blip,
        so NOT kept-last-good, NOT debounced).
 VERIFY: api.response {status:401} == Network ; table.version {rawErrorStatus:401,
           blipSuppressed:false, shownErrorStatus:401} ; row.status
           {text:"Authentication required"}.
 PASS = immediate on the first 401 check.

--- STEP 5 — real 403 -> "Insufficient permissions" IMMEDIATELY (PAGE-1) -------
 (Only if you can produce a real 403 — e.g. a login with limited RBAC / a namespace
  you lack rights on. Otherwise mark NOT PRODUCED.)
 LOOK:  row = "Insufficient permissions".
 VERIFY: api.response {status:403} ; table.version {shownErrorStatus:403} ;
         row.status {text:"Insufficient permissions"}.

--- STEP 5b — Background auth check: "Ready" vs "Reachable" (PAGE-1) -----------
 Why: the row status can come from TWO probes — /version (reachability) AND the
 background auth check (selfsubjectrulesreviews) that upgrades "Reachable" to
 "Ready". STEP 4/5 exercised the /version path; this checks the auth-probe path.
 GO:    PAGE-1, logged in.
 LOOK:  when BOTH probes succeed the row reads "Ready"; if /version is 200 but the
        auth probe hasn't confirmed yet it reads "Reachable"; a 403 on the auth probe
        reads "Insufficient permissions".
 VERIFY: Network shows selfsubjectrulesreviews = 200/201 ; api.response for it in
        console ; row.status text = "Ready".
 ASK HUMAN (optional): log out -> selfsubjectrulesreviews returns 401/403 ->
        row reflects "Authentication required" / "Insufficient permissions".
 HONEST NOTE: this auth-probe path is exactly where the SEPARATE slow-recovery bug
 lives (see STEP 7). Recovery of THIS status after re-login may lag ~60s on this
 branch; that lag is not a P0 defect, only the correctness of the shown status is.

--- STEP 6 — OPEN-GATE behavior (PAGE-3) --------------------------------------
 6a-0 (FRESH open + blip = retry once, not gate — OPEN_GATE_RETRY):
   Why: distinct from keep-last-good. On a FIRST open with no prior success, a single
   transient blip should be RETRIED once (jittered), not gated immediately.
   DO: hard-reload the app first (clears cached auth), set Throttling -> "Offline",
     then immediately CLICK the cluster NAME to open /c/<cluster>, and ~1s later set
     Throttling back to "No throttling".
   LOOK: the open does NOT slam straight to the access gate on the first blip; it
     retries and then loads the page once the network returns.
   VERIFY: console shows authgate.retry {status:502/408, failureCount:0,
     willRetry:true} (a retry happened) followed by authgate.decision {screen:'page'}.
   PASS = a transient blip on a fresh open is retried, not gated. (Timing is fiddly;
     if you cannot line it up, mark BEST-EFFORT and rely on the authgate.retry log.)
 6a (blip keeps the page):
   ASK HUMAN to be LOGGED IN first (reply 'logged in').
   CLICK the cluster NAME on PAGE-1 -> you navigate to /c/<cluster> (PAGE-3) and the
     cluster overview loads.  VERIFY: authgate.decision {screen:'page'}.
   DO: Network -> "Offline" ~2-3s while on PAGE-3, then online.
   LOOK: the page STAYS visible with a bottom-RIGHT "Reconnecting…" chip (it must NOT
     throw the full access gate for a single blip).
   VERIFY: authgate.retry {status:502/408, willRetry:true} ;
           authgate.decision {screen:'keep-last-good+chip', hadPriorSuccess:true,
             authErrStreak:1} ; chip.reconnecting {shown:true} ; DOM shows the chip.
 6b (real auth gates at once):
   ASK HUMAN: "Please LOG OUT now, then reply 'logged out'." WAIT.
   Still on PAGE-3 (or click the cluster name again): the centered ACCESS GATE must
     appear IMMEDIATELY.
   VERIFY: authgate.retry {status:401, willRetry:false} ;
           authgate.decision {screen:'gate', gateState:'expired', status:401} ; DOM = gate.
