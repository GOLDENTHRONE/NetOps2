==================================================
1. CORE RULE — SHARED CODE IS READ-ONLY
==================================================

The most important constraint:

DO NOT MODIFY SHARED CODE.

Shared code means any file/function/component that is used outside the health-local implementation, unless I explicitly approve that exact shared-file change.

Treat shared files as READ-ONLY for this entire task.

Before modifying ANY file:
1. Determine whether it is health-local or shared.
2. If shared, DO NOT modify it.
3. If a requirement appears to require a shared-file modification, STOP and explain:
   - which shared file would need modification
   - why you think it is required
   - what the alternative health-local implementation would be
   - what behavior/risk each option has
4. Wait for my explicit approval before touching shared code.

Do not "clean up" shared code.
Do not refactor shared code.
Do not rename shared functions.
Do not move shared logic.
Do not change shared types merely because it makes implementation easier.
Do not change APIs/fetching infrastructure.
Do not modify shared UI components.

If the feature can be implemented without touching shared code, that is ALWAYS the preferred solution.

==================================================
2. WORK ONE LOOP AT A TIME
==================================================

The Application Health work is divided into independent loops.

You MUST NOT implement multiple loops together.

For each loop, use this exact process:

STEP A — UNDERSTAND
Inspect the repository and understand the current implementation relevant to ONLY this loop.

STEP B — VERIFY
Verify the actual current behavior from the code and existing tests.

Do not assume the implementation matches the plan.

STEP C — PROPOSE
Tell me exactly:
- what currently happens
- what needs to change
- why the change is required
- exact files you intend to modify
- exact functions/sections you intend to modify
- files that must remain untouched
- expected health-state impact
- expected informational impact
- expected diagnosis impact
- API/fetch impact
- aggregation impact
- deduplication impact
- UI impact
- test impact
- risks/regressions
- what will explicitly NOT change

STEP D — STOP
After presenting the loop plan, STOP.

Do NOT write code.

Wait for my explicit approval.

==================================================
6. HEALTH SEMANTICS
==================================================

Be extremely careful about the distinction between:

HEALTH VOTE
- Can affect application health/state.

INFORMATIONAL
- Can be displayed/countable but must not affect application health.

DIAGNOSIS
- Explains a likely correlation/evidence.
- Must NEVER itself vote on application health.
- Must NEVER alter application state.
- Must NEVER affect worst-of-roots aggregation.

Do not convert an informational resource into a health vote unless that exact behavior is explicitly approved.

Do not make a diagnosis merely because a resource is unhealthy.

A diagnosis requires the agreed correlation/evidence rules for that loop.

==================================================

Tests must prove the intended behavior AND protect existing behavior.

For every loop, identify:

- new regression tests required
- behavior that must remain unchanged

If an existing test contradicts the newly approved requirement, explain why the assertion must change.
