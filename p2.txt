==================================================
GOAL
==================================================

Add an Application Health model to the Application/Project table.

The health calculation must be centralized in ONE pure TypeScript evaluator:

    evaluateApplicationHealth(...)

Both:
1. the Health table cell
2. the Health popover

==================================================
1. HEALTH MODEL
==================================================

HealthStatus:

    'healthy'
    'degraded'
    'progressing'
    'unhealthy'
    'unknown'

ObservabilityStatus:

    'complete'
    'partial'
    'loading'

Severity:

    'error'
    'warning'
    'info'
    'unknown'

Health precedence:

    unknown > unhealthy > progressing > degraded > healthy

However, IMPORTANT:

Observability and health are different concepts.

A Kubernetes API error such as:
    401
    403
    404 where the API/resource is expected
    500
    502
    503
    504
    timeout
    loading
    truncated list

must NOT be converted into "unhealthy".

It means that we cannot reliably observe/evaluate that resource.

The resulting application can therefore become UNKNOWN because of insufficient evidence.

Preserve known unhealthy findings from other observable clusters/resources even if the aggregate application status becomes UNKNOWN.

Example:

    Cluster A = unhealthy because Pod is CrashLoopBackOff
    Cluster B = unknown because Pods API returns 403

Application status = UNKNOWN

But the popover MUST still show:

    Observability gap:
      Cluster B / Pods / 403 Forbidden

    Known finding:
      Cluster A / Pod / CrashLoopBackOff

Do not hide known failures merely because another cluster is unobservable.

==================================================
2. APPLICATION MEMBERSHIP
==================================================

Membership remains namespace-scoped.

Application ID:

    namespace.metadata.name

For multi-cluster:

    collapse applications with the same namespace name across clusters.

An application contains resources from that namespace across all configured clusters.

Do NOT introduce custom label selectors or dynamic filters.

Authoritative membership:

    Any Kubernetes resource located in the namespace belongs to the Application.

==================================================
3. HEALTH-BEARING RESOURCE KINDS
==================================================

ONLY these resources vote on application health:

    Pod
    Deployment
    StatefulSet
    DaemonSet
    Job
    PersistentVolumeClaim

ReplicaSet is SUPPORTING ONLY.

It must NOT independently contribute to health.

Use ReplicaSets only for ownership attribution:

    Pod -> ReplicaSet -> Deployment

Supporting resources that must NOT vote independently:

    ReplicaSet
    Service
    Endpoints / EndpointSlice
    CronJob
    HPA

Optional:

    Ingress
    OpenShift Route

Non-health-bearing:

    ConfigMap
    Secret
    Role / RoleBinding
    ResourceQuota / LimitRange
    NetworkPolicy

These must never independently make an Application unhealthy.

==================================================
4. RESOURCE HEALTH EVALUATION
==================================================

POD

Use actual Kubernetes runtime state as the primary ground truth.

Evaluate:

    phase
    Ready condition
    container waiting reasons
    container terminated reasons
    restart/crash information

Examples:

    Running + Ready -> healthy
    CrashLoopBackOff -> unhealthy
    OOMKilled -> unhealthy
    ImagePullBackOff -> unhealthy
    ErrImagePull -> unhealthy
    failed container -> unhealthy
    ContainerCreating -> progressing
    initializing/creating -> progressing
    unknown phase/condition when it prevents reliable evaluation -> unknown

Do not infer Pod health from its owner.

--------------------------------------------------

DEPLOYMENT

Evaluate using:

    spec.replicas
    status.availableReplicas
    status.updatedReplicas
    status.observedGeneration
    Progressing condition
    rollout deadline condition

Examples:

    desired == available and rollout observed -> healthy

    desired > available but workload is transitioning ->
        degraded/progressing according to actual Kubernetes state

    ProgressDeadlineExceeded ->
        unhealthy

Use actual status conditions rather than arbitrary time-based assumptions.

--------------------------------------------------

STATEFULSET

Evaluate:

    spec.replicas
    status.readyReplicas
    status.currentRevision
    status.updateRevision

Examples:

    3 desired / 3 ready -> healthy
    2 desired / 3 ready -> degraded

--------------------------------------------------

DAEMONSET

Evaluate:

    status.desiredNumberScheduled
    status.numberAvailable
    status.numberUnavailable

IMPORTANT:

A DaemonSet with:

    spec/desired replicas = 0

is a legitimate healthy state.

Do NOT classify zero desired replicas as unhealthy.

--------------------------------------------------

JOB

Evaluate:

    status.failed
    status.active
    status.succeeded

Examples:

    failed > 0 -> unhealthy
    active > 0 -> progressing
    succeeded > 0 and no failure -> healthy

--------------------------------------------------

PVC

Evaluate:

    status.phase

Examples:

    Bound -> healthy
    Pending -> degraded/progressing
    Lost -> unhealthy
    unknown -> unknown

==================================================

Implement ownership tracing so findings are useful to humans.

For example:

    Pod
      -> ReplicaSet
        -> Deployment

A finding should identify:

    kind
    name
    namespace
    cluster
    reason
    message
    owner

Example:

    Owner: Deployment/caserver

Do not incorrectly attribute a Pod directly to an Application if a useful workload owner can be resolved.

Expose whatever is required, for example:

    isTruncated

Do not invent parallel data-fetching architecture if the existing hooks can be extended.

Examples:

        observability gap

==================================================
7. EMPTY / SPECIAL CASES
==================================================

If the namespace contains zero health-bearing resources:

    Application health = healthy/neutral as defined by the existing spec

UI should show:

    No workloads

Do NOT show a green check merely because the calculation happened successfully if the intended UX is a neutral empty state.

If only non-health-bearing resources exist:

    No workloads

Do not count Secrets, Services, ConfigMaps, RBAC, etc. as workloads.

If a health-bearing kind is legitimately absent, that absence alone must NOT cause UNKNOWN.

Example:

    No DaemonSets

is completely valid.

==================================================
8. MULTI-CLUSTER AGGREGATION
==================================================

Applications with the same namespace name across clusters must be aggregated.

Use:

    unknown > unhealthy > progressing > degraded > healthy

for final status precedence.

But preserve findings and observability gaps from each cluster.

Example:

    Cluster A = healthy
    Cluster B = degraded

Application = degraded

Example:

    Cluster A = unhealthy
    Cluster B = unknown

Application = unknown

BUT:

    findings must include the unhealthy Cluster A finding
    gaps must include the Cluster B observability failure

Do not lose diagnostic information because of aggregation.
