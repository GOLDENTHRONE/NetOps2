--------------------------------------------------
CORE ARCHITECTURAL QUESTION
--------------------------------------------------

We need to answer:

"What does it actually mean for a Kubernetes Application to be healthy?"

Do NOT answer this by simply creating a fixed list such as:

Health-bearing:
- Pod
- Deployment
- StatefulSet
- DaemonSet
- Job
- PVC

Supporting:
- Service
- EndpointSlice
- Endpoints
- Ingress
- Route

Never health:
- ConfigMap
- Secret
- RBAC
- NetworkPolicy
- ResourceQuota
- LimitRange

That classification may be useful as a starting hypothesis, but it is NOT sufficient.

Instead, determine whether the health model should be based on the semantic role and relationship of a resource.

For example:

A Service is not inherently "healthy" or "unhealthy" as an application.
It is evidence about connectivity/discovery.

An EndpointSlice is not itself the application.
It may provide evidence that traffic has usable backends.

An Ingress/Route is not the application.
It provides evidence about external exposure/routing.

A ConfigMap may be essential to a workload, but its existence alone does not mean the application is healthy.

A Secret may be essential, but its mere existence should not become an application-health vote.

A PVC may be critical for a StatefulSet, but should not automatically be treated the same way for every application.

Therefore, investigate whether we should model:

    Application
       |
       +-- Workload / execution resources
       |
       +-- Supporting resources
       |
       +-- Configuration/dependency resources
       |
       +-- Connectivity/exposure resources

but derive these relationships from actual Kubernetes semantics rather than blindly hardcoding one topology.

- Pod

For each resource type, answer:

5. Is it normally owned by another resource?

--------------------------------------------------
HEALTH VS CONNECTIVITY VS CONFIGURATION
--------------------------------------------------

Separate these concepts.

I want three conceptual categories:

1. PRIMARY APPLICATION HEALTH

Evidence that the application workload itself is functioning.

Examples may include:
- desired vs available replicas
- Pod readiness
- Pod phase
- container readiness
- controller conditions
- Job completion/failure
- StatefulSet readiness
- DaemonSet availability
- other workload-specific runtime state

But determine the correct Kubernetes semantics for each resource.

2. SUPPORTING / CONNECTIVITY EVIDENCE

Evidence that the application can be reached or exposed correctly.

Potential examples:
- Service
- EndpointSlice
- Endpoints
- Ingress
- OpenShift Route
- Gateway/API resources if relevant

These should NOT automatically receive an independent "health vote" just because they exist or have a particular status.

Instead determine when they should:
- contribute to diagnosis,
- provide supporting evidence,
- become a health-affecting dependency,
- or remain informational.

For example:

A healthy Deployment with a missing/empty Service backend is different from an unhealthy Deployment.

Do not collapse those cases into the same condition.

3. CONFIGURATION / POLICY / ENVIRONMENT

Potential examples:
- ConfigMap
- Secret
- RBAC
- NetworkPolicy
- ResourceQuota
- LimitRange
- other policy/configuration objects

Determine whether these should:
- never directly vote on application health,
- produce diagnosis,
- produce informational messages,
- or become health-affecting only when there is concrete evidence that the workload is impacted.

The key distinction is:

RESOURCE STATE != APPLICATION HEALTH

A resource can be unhealthy without the application itself being unhealthy.
